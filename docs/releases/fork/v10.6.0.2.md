## Live Activity and Dynamic Island

**Toggling the Live Activity off and back on now works the first time.** It used to leave nothing
showing until you toggled several more times. `end()` is async and was launched detached, so it ran
*after* the next ~1 Hz tick had already started a fresh activity — and because it ends every NOOP
activity rather than the one it was asked about, it killed the one just re-enabled. Whether the
start survived was down to task ordering, which is why repeated toggling eventually appeared to
work. Two things made it fire routinely rather than rarely: every tick while off queued another end
(~1/s, so seconds off meant a backlog of killers), and the re-adopt on launch took the first
activity unfiltered, so an already-ended handle could be adopted and swallow every later update —
no visible activity, and no attempt to start one.

Start/end epochs now carry a generation counter, an end whose generation is stale drops its own
request, redundant ends collapse to one per generation, and only an `.active` activity is re-adopted.
Because the fix sits on the presentation policy's suppress path, it also covers the sleep-window
pause below.

**The heart rate shows in the Dynamic Island's minimal presentation,** instead of just a heart icon.

**The Lock Screen slows down while the phone is locked.** Beat-level movement is unwatchable there,
and on an Always-On display every push repaints the Lock Screen — a measurable all-day battery cost.
Locked, it pushes once a minute showing that minute's mean HR; unlocked, it stays live at ~2 s. The
interval is configurable in Settings → Live Activity, and **0 restores fully-live behaviour**.

**The Lock Screen and Dynamic Island pause over the sleep window,** rather than displaying through
the night.

## Battery

**Data-driven re-scores are deferred while the phone is locked** and settle once at unlock, instead
of running against a screen nobody is looking at. The sleep window is the same source of truth the
presentation pause uses, so the two can never drift apart.

## Coach and Today synthesis

**A coach-written paragraph on every app open,** always expanded, with Ask-the-Coach always visible
and 1h / 3h / 6h horizons that link into the Coach.

**One unified Refresh** — sync kick, forced re-score and coach regeneration behind a single control,
with proper Markdown rendering and an on-demand refresh button.

**Each provider gets its own API-key slot,** so switching model no longer means re-entering a key,
and a request that times out retries once against a faster model.

The Kotlin twins of the AI-coach changes are carried too, so the two platforms don't drift — though
no APK is built from this fork.

## Build and release tooling

**`Tools/build-release-branch.sh` builds against the upstream remote.** It was hardcoded to
`origin/main` — the *fork's* mirror — while `sync-upstream.sh` rebases features onto `upstream/main`.
The release was being stacked onto whatever the mirror last saw, which is a perfectly clean merge
that silently omits upstream commits. This is why a freshly-fetched 10.6.0 would not have appeared
in the build.

**`RELEASE_BRANCH` overrides the integration branch name,** so a build works while `release` is
checked out in another worktree — git refuses to update a branch that is, and the failure was a
fatal that said nothing about how to proceed.

**Two recurring merge conflicts fixed at the source,** rather than re-resolved on every rebuild: a
`bpm` unwrap that two branches each added their own version of, and the Live Activity fix, which now
stacks on the presentation-policy branch instead of conflicting with it. A full rebuild is now
conflict-free.

**Documentation:** [`docs/FORK-RELEASE.md`](../../FORK-RELEASE.md) covers the procedure, the
versioning rule, and the traps — the Team ID `OU`-vs-`CN` trap, 7-day provisioning expiry, and the
fact that no CI covers app-target Swift.
