## Sleep: the night was being cut back onto the previous day

19.14's fill did not help, and its new line showed why:
`sleepTab: night lag — shown=2026-10-17 scoredDay=2026-10-18 blocks=83 blocksNewest=2026-10-17
sleepsNewest=2026-10-17`. BOTH lists ended on 10-17, so the store itself held no block ending on
10-18, even though the day row (542 min, Rest 93 on Today) was right.

Mechanism: at 22:43 on 10-17 a light pass ran with the 10-17 window still open. It detected the
start of the night as a second 10-17 block (`matched=2` from then on). Every later pass that scored
both days detected the night twice with the same startTs: the opening stretch, clipped at the 10-17
window's edge, and the whole night in 10-18's window. Both upserted into one row. The pass writes
newest-first, so the clipped copy landed last and pulled the night back onto 10-17. Passes that
scored 10-18 alone (the abandoned `scanned=1/21` ones) wrote the whole night, which is when 93
appeared on the Sleep tab.

Fix, two layers:
- The pass keeps one block per start, the latest-ending (`IntelligenceEngine.longestPerStart`),
  with a rare-event line `sleepWrite: kept the longest of N same-start block(s)` when it collapses.
- The store refuses a non-edited same-start candidate that ends ≥ 2 h EARLIER than the stored row
  (a pass scoring only the earlier day). Minute-scale re-stages and lengthenings still land.
- Self-repairing: the next pass that scores 10-18 rewrites the row to the whole night.

Not changed: the analytics day window still SEES the opening stretch on the earlier day; this
build stops it from overwriting the night.
