Everything upstream ships in v10.6.0, plus the nine local feature branches below. These notes cover

## Reinstalling this build

**Clear the provisioning profiles first, then build.**

```bash
rm -f ~/Library/Developer/Xcode/UserData/Provisioning\ Profiles/*.mobileprovision
```

A free personal team issues 7-day profiles, and Xcode reuses an existing valid one rather than
minting a new one — so rebuilding does *not* reliably reset the clock. Verify the reset took by
reading the profiles' `CreationDate` (see FORK-RELEASE step 4). The app stops launching at expiry
regardless of anything in the code.

## New: the synthesis can see the data it already had (`feature/synthesis-horizons`)

**The gap.** The context builder read five columns off each `DailyMetric` row — charge, effort,
sleep hours, HRV, resting HR — and discarded the rest of the row it was already holding. So the
model was asked to "analyse my sleep" while being shown a single sleep *duration*: no stages, no
efficiency, no disturbances, no SDNN, no skin temperature, all of which were sitting unread in the
same rows. Separately, the app computes training load, a sleep-debt ledger and personal baselines
for its own screens, and told the model none of it — leaving it to eyeball fourteen numbers and
infer a trend it had no way to compute. The Today synthesis and the Coach share
`buildFullContext()`, so both were reasoning from the same thin slice.

**The change.** A third opt-in, `includeDerivedTrends` (`ai.includeDerivedTrends`), gated behind
`dataConsent` exactly like the Lab Book toggle, default **OFF**. When on:

1. **Each day line widens** with the held-but-unsent columns — deep/REM minutes, sleep efficiency,
   disturbances, SDNN, skin temperature.
2. **A `DERIVED TRENDS` block is appended** — training load (chronic/acute/balance via
   `TrainingLoadEngine`), the sleep-debt balance against need (`SleepDebt.ledger`), the latest
   night z-scored against the wearer's own baselines (`Baselines.foldHistory` + `deviation`), and a
   data-density line.

Every figure is a pure function over the days already in the context. **No new store read, no new
network call, no new data category leaving the device** — this widens *resolution*, not scope, and
rides the same text-only channel the metrics summary already used.

**Three ways a formatter here can lie, each closed and pinned by a test:**

- **A nil field is absent, never zero.** A night that recorded no deep sleep must not render as a
  night of *zero* deep sleep — a different claim, and one the model would act on.
- **`skinTempDevC` is bimodal.** Strap nights bank a deviation from baseline; CSV/Apple imports
  write an absolute wrist °C into the same column. Values are labelled by magnitude
  (`VitalBands.isAbsoluteSkinTemp`) rather than asserting one meaning for both, which would
  misreport every row of whichever kind lost the coin toss. (The unambiguous `skinTempC` column from
  upstream #1636 is **not** available on this branch's base — it postdates it.)
- **A roll-up without enough history is omitted, not stated.** Three days yield a sleep-debt line
  and an explicit "thin history" caveat, never a training-load balance the engine has no basis for.
  The `TrainingLoadEngine` state (`building` vs `established`) is passed through as a qualifier
  rather than flattened away.

**Scope note.** Because `buildFullContext()` also backs `refreshSynthesis()`, this feeds the Today
synthesis paragraph as well as the Coach chat. That is intended — the synthesis is the surface the
richer data was asked for — and the toggle copy names both so a user is not surprised by where it
takes effect. The toggle lives on the Coach screen beside the two existing consents.

**What to watch on the next build.** Whether three consent toggles on one screen is one too many:
all three now gate derived, on-device, summary-only data, and the case for folding this into the
existing `includeOnDeviceSignals` switch is real. Deliberately not done here, because reusing that
key would silently widen a consent existing users already set for something narrower.

## Not done in this build

- **No Android twin.** `AiCoach.kt` still emits the narrow day line and no trends block, so the
  Kotlin and Swift coach contexts now differ. This is iOS-only by request and is a knowing,
  temporary break with the cross-platform parity contract — the twin is the follow-up. No *stored*
  data or analytics value diverges; the difference is confined to prompt text.
- **No `whatsnew` entry.** The new toggle is user-visible and warrants one (with `title_locales`)
  in whichever upstream-facing release carries it.
- **`docs/FEATURES.md` still has no AI Coach section at all** — a pre-existing gap, not one this
  build introduces, but it means there is no feature-guide entry to extend.

App-target Swift throughout (`Strand/AI`, `Strand/Screens`), so **no default CI covers any of it** —
`swift-packages.yml` does not compile app targets and `app-build.yml` is disabled. Both targets were
compiled locally.

The 11 new tests cover the two pure formatters (`dayLine(_:wide:)`, `derivedTrendsBlock(days:)`),
which are `nonisolated static` precisely so they can be pinned without a store, a provider or a live
engine. They include a **positive control** (`testLongHistoryEmitsTrainingLoad`): without it, the
thin-history test would pass just as happily if the load block were dead code that never emitted.

**The one failure is upstream's, not this fork's.**
`SkinTempAbsoluteDisplayTests.testTheSecondaryLeadsTheCaptionSoItSitsUnderTheValue` hardcodes
`"2026-08-25"` and renders `24 Aug` — a date/timezone off-by-one on a UTC-7 machine. Reproduced on
**pristine `upstream/main` (`35182be5`) in a clean worktree with no fork branches merged**, which is
what settles it: it first appeared to pass on the feature branch, but only because that branch
predates the file and zero tests ran there. Worth stating precisely, since this build also touches
skin-temperature formatting — different call sites, and the clean-upstream run is the evidence.

**Build is 256** (not the 249 the fork branch stamps): upstream staged to 255, and the recurring
`project.yml` build-number conflict resolves upward, per FORK-RELEASE. A build number may only
increase or iOS refuses the install.

**Not verified on hardware.** This build was compiled and unit-tested; it has **not** been run on a
phone or exercised against a strap. Nothing here touches BLE, offload or scoring — the change is
confined to prompt-text assembly — so the strap-side risk is low, but "low" is not "measured". The
checks that need a device: that the new toggle appears and persists, that turning it on visibly
changes the Today synthesis, and that a wearer with thin history sees the hedged text rather than a
confident trend.
