# 11.8.0.18.27 (build 428)

Effort back on upstream's yardstick.

## "My effort suddenly shows 21" — attributed

The computation was never modified: `StrainScorer.strain` (Edwards TRIMP) is the one shared
function, and the engine's stored path is byte-untouched. What diverged was an INPUT on the live
path: the Today views' live Effort estimate passed Tanaka-from-age as HRmax, ignoring the manual
override the engine scores against (`hrMax=179.3(provided)` in every effort ledger line). An
override is normally set because the real max is above the formula, so the live value sat on the
smaller yardstick and scored HIGH — and `effectiveEffort` (max of live and stored) then always
displayed it. Upstream fixed exactly this as #2460, AFTER the fork's v11.8.0 base, so the fork
never received it. Two things made it visible now: 18.25 propagated the ring's live value to the
strip and widgets (so the wrong-yardstick number stopped being a ring-only quirk), and slow
mornings keep the stored value behind all day.

## The port (verbatim)

`Profile.effortHRmax` (override → Tanaka → nil, exactly as `AnalyticsEngine` resolves it), both
Today views read it, and upstream's `EffortHRmaxOverrideTests` (5) comes along. Live and stored
now score against one number, so the live estimate converges to what the next pass persists
instead of outvoting it. No engine change; no display-path change beyond the input.

## Verification

Both app targets compile; EffortHRmaxOverrideTests (5), RepositoryLiveTargetsTests (7). On
device: today's Effort should drop from the inflated figure to the same value the evening pass
writes, and ring/strip/widgets stay in agreement. Tomorrow's log: the `effort score … hrMax=…
(provided)` value and the displayed number tell one story.
