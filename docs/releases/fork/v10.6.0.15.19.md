## The "Add a cup" button logged nothing

Reported from the device on 15.18: tapping the water reminder's cup button did not move the count.

The button, the action and the handler were each correct. The bug was WHERE they were installed.
`setNotificationCategories` and `installHydrationReminderSink()` were wired in `StrandApp.swift`,
which is the **macOS** `@main` — excluded from the iOS target in `project.yml`. On iOS the sink
stayed nil and `NotificationPresenter` dropped every response on its `guard`. The buttons still
rendered, because `HydrationReminder.post` registers its own category just before posting; that is
exactly what made it look like it should work.

Introduced by the 15.18 sync-driven rewrite, which moved the reminder off calendar triggers and
added the sink on the macOS launch path only.

Both are now wired in the iOS `@main`, in `init` rather than a `.task` on the root view: iOS
delivers an action response to a **cold-launched** app before any view renders — and tapping the
button is itself what launches the app — so a scene-lifecycle install would race precisely the tap
it exists to handle.

`NotificationActionWiringTests` reads both `@main` files and asserts every launch step is present in
each, plus that the iOS install precedes the scene body. This class of bug is invisible to a
behavioural test: both platforms compile and the unit test for each part passes. Verified against
the pre-fix commit — it fails on exactly the two missing lines.

**Still unverified on hardware.** The tap path needs an install to confirm; compile success proved
nothing here, which is the whole point of the bug.

## Water n/t replaces the sleep target in the widgets

Maintainer instruction. Sleep need is a fixed figure that does not move through the day, so it spent
a daytime cell repeating itself; water is both actionable and the one number the reminder's buttons
change. Sleep keeps its Live Activity column and its in-app row.

Affects the three targets-widget families that show four cells (rectangular, small, medium).
`accessoryInline` was already Cal + Steps only.

The snapshot carries **half-cups** (the tracker's own resolution); the face renders **whole cups,
rounded down**. That quantization is load-bearing for battery, not just for width:
`renderedContentChanged` dedups on the RENDERED string, so a half-cup that does not move the
whole-cup figure costs no WidgetKit reload request — roughly halving what this feature can spend
against iOS's daily refresh budget at a ~16–21 cup target.

Republishes on `hydrationSeq`, the single funnel every hydration write already bumps (#989), so one
hook covers the notification action and the in-app +/- alike. Deliberately **not** scenePhase-gated:
the notification action is handled with the app backgrounded, which is the case it exists for. The
cost is bounded — deliberate taps, a handful a day, and no reload requested unless a rendered string
actually moved.

Answering the maintainer's own question ("it doesn't have to immediately update if it saves
battery"): here both are available, because the dedup makes the immediate publish nearly free.
