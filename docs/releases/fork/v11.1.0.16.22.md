# 11.1.0.16.22 (build 334)

Two reports from build 333, both correct. The second is a defect 333 created rather than one it
missed.

## "I don't see the customization params for what a normal day looks like"

There were none. The anchor shipped as a code constant, and — the part that mattered —
`DayQualityPrefs.config`, the ONE builder the scoring pass uses, never applied it at all.

Three consequences, all fixed:

- **Five new settings** (steps, calories, effort, water, sleep), clamped on READ so a corrupt or
  hand-edited value cannot move the zero point somewhere nonsensical. Each falls back to the scorer's
  own default rather than a restated literal, so the two cannot drift.
- **`config` now carries the anchor.** Without it the card — which reads the anchor directly — and the
  stored series computed *different numbers for the same day*.
- **The anchor is in `configFingerprint`.** Without that, tuning zero would change future scores while
  leaving history on the old zero: a trend mixing two definitions of zero with nothing on screen to
  say so. Omitting an input from that string is exactly how the 260908 migration silently failed.

The anchor is also printed in the settings card's **collapsed** header — *"Zero is 4000 steps · 1600
kcal · effort 8 · 8 cups · 7h sleep"*. A collapsed panel is the right home for weighting knobs and
the wrong one for the definition of zero: it is what the whole number means, and a reader needs it to
interpret every score on the page above.

`Execution share` is removed from the card. The scale no longer splits a fixed 100 points between two
halves for it to divide, so the slider moved nothing — and a control that moves nothing is worse than
no control.

## "The changes haven't propagated below to the trends sections"

Also correct, and worse than it looks. Build 333 made the card headline compute **live** and left the
trend chart, week summary, calendar strip and streaks reading the **stored** series. One screen
showing two formulas at once is a worse state than the consistent-but-wrong one before it. The 333
headline fix treated the symptom.

The root cause is now **measured rather than inferred**: the 260908 log contains **no `day-quality:`
line at all** across 18 passes — nor any line from that block's siblings. The pass never ran, and
there was no way to tell whether it was gated, latched, or simply finding nothing to do.

    $ grep -c "day-quality:" noop-strap-log-260908-2112.txt
    0
    $ grep -c "analyzeRecent cost" noop-strap-log-260908-2112.txt
    18

So two changes:

- **Every exit from `scoreDayQuality` names its reason** — no history / already scored / nothing to
  score / nothing scorable — and the success line carries `rescoreAll` and the fingerprint. A silent
  skip on the only path that writes the number the whole tab is built on is precisely the gap the
  diagnostic rules exist to close: prefer a line that names the reason over inferring it from an
  absence.
- **The Day tab can reconcile itself.** `rescoreDayQualityNow()` is called when `configChanged`,
  awaited before the read so the first paint shows one formula rather than flashing the old numbers
  and correcting itself. Idempotent and latched to once per (day, config), so it is a no-op on every
  visit after the first. The scoring pass is the only writer and runs on the engine's own schedule;
  without this the tab could show the mismatch indefinitely with no action available to resolve it.

## A stored preference that changed meaning gets a new key

Build 332 wrote `125` to `dayquality.overshootCapPct` under the old semantics (a ceiling on
achievement). Read as the *new* overshoot MULTIPLE, 1.25 silently caps the scale's ceiling at **77
instead of 100** — so on an upgraded install the top of the scale was unreachable and nothing said so.

Namespaced to `dayquality.v3.overshootCapPct`. The old value was a valid answer to a different
question, not something to migrate by guess; a test pins that the retired key is ignored rather than
reinterpreted.

## A test of mine that failed correctly

The 333 guard asserted "**exactly one** call site" for the scoring pass, and broke the moment the
on-demand re-score added a legitimate second caller. It now asserts the actual property — that
**every** call site sits outside `if !lightPass` — which is the same "counting was the wrong
property" correction the `CBCentralManager` construction-site test needed in 16.19. Counting is
almost always the wrong shape for these.

## What the next log must show

1. **A `day-quality:` line.** Any line at all — this is the whole point of the diagnostics. If it
   reads `scored N day(s)`, the migration ran. If it reads `already scored … under this config`
   without ever having scored, the latch is being set without a write and that is the next bug. If
   there is still NO line, the pass is not being reached and the gate analysis is wrong.
2. **The trend, week view and calendar agreeing with the card.** The specific symptom to re-check:
   a −22 on the card must appear as −22 in the week view.
3. **The five normal-day steppers present** under Score settings on the Day tab, with the zero point
   visible in the collapsed header without expanding anything.
4. Re-score CPU back under ~900 s with `gave up` firing in seconds (the 16.20 launch-seed fix, still
   unverified in the field).
5. Ignore `reqToBuild max` if it reads exactly **900 s** — still under suspicion as our own clamp.
6. Carried forward: the 54-hour light-pass read window is the largest known battery cost and needs a
   byte-identical-score oracle before it can be narrowed.
