# 11.1.0.16.23 (build 335)

The same symptom reported twice: the score card correct, everything below it — trend chart, week
summary, calendar, streaks — showing values from a retired formula. Build 334's repair was gated on
the wrong signal. This build stops trusting that signal.

## The screenshot dates itself

    DAY QUALITY TREND    MEAN 55    BEST 77    DAYS 13
    Consistency: 23 of 25 above zero, 92%

**`BEST 77` is exactly 50 × 1.25 + 15** — the ceiling of an overshoot cap that no longer exists (the
current multiple is 1.7, which gives 100). Twenty-five dense days, every one above zero, on a scale
whose zero is an ordinary sedentary day.

No current setting can produce that series. It was written under a formula two revisions back, and
nothing had rewritten it.

## Why 334's repair never fired

It asked `DayQualityPrefs.configChanged`. That flag records that a pass **ran**, not that the stored
values match the current formula — so a pass that latched under one formula leaves the series looking
complete to the next one, the repair never triggers, and the chart keeps showing numbers no code path
can produce.

The latch has now been the wrong mechanism **twice** for exactly this reason. It is no longer trusted
for this decision.

## The check is now on the values

Two independent tells, either sufficient:

1. **A value outside −100…+100.** The published scale is that range by construction, so anything
   beyond it came from another scale. Proof on its own, at any sample size.
2. **Nothing at or below zero across 20+ days.** Zero is an ordinary day, so a real series crosses it;
   the retired 0–100 scale could not go below zero at all.

The second tell is gated on a generous sample deliberately. A false positive costs one idempotent
re-score; flagging a genuinely good fortnight would re-score on every visit. The asymmetry decides
the threshold.

When either fires, the tab calls `rescoreDayQualityNow(force: true)`, which bypasses **both** the
once-per-day latch and the incremental "already stored" skip, re-deriving every finished day from its
own rows — then re-reads, so the first paint shows one formula rather than correcting itself.

`seriesLooksStale` is pure and static, and its test uses **the reported series verbatim** — the 25
values from the screenshot, best 77. The exact case that shipped twice now fails the build if it can
ever be stored again. The rule is also pinned NOT to fire on a real signed series, a short good
stretch, a day sitting exactly at zero (zero is reachable, not a sentinel), or an empty series on
first run.

## A test of mine that failed correctly, again

The 334 guard asserted the literal string `func rescoreDayQualityNow()`. It broke the moment that
function gained a `force:` parameter — a test pinned to a signature *spelling*, failing on the change
that strengthened the very thing it guarded. Now matches the name and separately asserts the force
path exists.

That is the third time in this stretch a test has been written against the wrong property (a count of
call sites, a count of `CBCentralManager` sites, a signature spelling). The pattern is worth naming:
when the assertion is about *shape* rather than *behaviour*, it fails on improvement as readily as on
regression.

## Verification

macOS and iOS both build. **1,864 app-target tests pass** apart from the known
`SkinTempAbsoluteDisplay` timezone flake.

## What the next log must show

1. **A `day-quality:` line.** Still the single most important thing, and still unobserved in the
   field. `scored N day(s)` means the re-derivation ran. `already scored … under this config` without
   a preceding score means the latch is being set without a write. No line at all means the pass is
   not being reached and the gate analysis is wrong.
2. **The trend crossing zero**, and its BEST no longer reading 77. A best of exactly 77 in a future
   log means a stale-cap series was stored again despite the new guard.
3. **The five normal-day steppers** under Score settings, with the zero point in the collapsed header.
4. Re-score CPU under ~900 s with `gave up` firing in seconds (16.20's launch-seed fix, still
   unverified in the field).
5. Ignore `reqToBuild max` at exactly **900 s** — still suspected to be our own clamp.
6. Carried forward: the 54-hour light-pass read window, the largest known battery cost, needs a
   byte-identical-score oracle before it can be narrowed.
