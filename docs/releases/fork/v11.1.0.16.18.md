# 11.1.0.16.18 (build 330)

A macOS regression fixed properly this time, week-in-review on both per-metric tabs, and the health-sync
number measured rather than guessed at.

## The macOS Bluetooth prompt: 260903 fixed the wrong layer

Reported: building the project launches the macOS app and it asks for Bluetooth permission again —
the thing 16.1 was supposed to have removed.

The report is right and the earlier change was genuinely incomplete. 260903 gated
`connectFromSystem`, the path that scans and connects, and **its tests still pass**. But the macOS
permission prompt does not come from connecting — it comes from **instantiating a
`CBCentralManager`**, which `init` did unconditionally. The gate was one layer too high. The scan and
the connect attempts did stop, which is why it looked fixed; the reported symptom did not.

`central` is now built **lazily, on first real use**. All 40 existing `central.` call sites read
through a computed property and are unchanged, so a deliberate Connect from the UI builds the client
on the spot. iOS still constructs eagerly in `init`: there, being ready to restore a background
connection at launch IS the product.

Both initializers matter — the test/preview one too, because `StrandTests` is *hosted* by the macOS
app, so an eager client raised the prompt on every test run as well as every build.

One subtlety: the unauthorized-settle diagnostic read `central?.state`, which on a lazily-built
client is a *construction*. It would have raised the very prompt this avoids, from the code whose
only job is to report on permission. It now checks existence first.

**The tests caught a real mistake while being written.** My first version asserted a *count* of
construction sites and failed at 3, because I had forgotten the second initializer. Counting was the
wrong property anyway: they now assert that every eager site sits inside `#if os(iOS)`, which is what
actually keeps macOS silent.

## Week in review, on the Day and Sleep tabs

In the Trends page's own language — the liquid vessel, the count-up number, the pip bar — built into
the shared `ScoreTrendSection` so both tabs get the identical card and neither can drift.

Three rows instead of Trends' Charge/Effort/Rest trio, because there is one metric per tab: this
week, last week, and the signed change. The delta uses the same like-for-like arithmetic the chart
footer uses, so two figures on one screen cannot disagree.

**The card always compares 7 against 7**, whatever the chart's window selector says. The footer under
a 30-day chart legitimately compares 15 vs 15, but a card headed "Week in review" reading fifteen
days because the picker moved would be the same mislabelling as the 16.15 "prev 7" bug. A test pins
that the card's window cannot follow the chart's. It hides unless both weeks are complete.

Down-weeks are neutral grey, not red: a quieter week is not a failure.

## Health sync: measured, not fixed

The log's `avgSyncMs=27233` — 27 seconds a sync — looks alarming, and the obvious read is "sixteen
sequential HealthKit queries, gather them concurrently". That may well be right. It is not yet
*measured*, and the aggregate cannot distinguish three causes that call for opposite changes:

- the **reads** dominate → gather the sixteen queries concurrently;
- the **write-back** dominates → that is our own writes, and the lever is writing less often;
- the **repo refresh** dominates → not HealthKit at all, and it belongs with the re-score work.

`syncMillis` is also **wall time, not CPU**, and a sync is mostly `await`. Time parked on an await is
latency, not battery — so even a large total does not by itself establish a drain. That is precisely
what the single number hid.

So this build adds the three-way phase split and changes nothing else. Shipping the concurrency
rewrite on the strength of a number that cannot pick between the three is the speculative fix the
instrumentation-first rule exists to stop.

Left alone deliberately, and worth recording why: the **168 empty wakes** are spurious HealthKit
observer notifications, already handled the cheap way (one anchored query, then return), and the **32
coalesced** ones are the existing 15-minute coalescer working. Neither is where the 27 seconds is.

An implementation note: the phases are stamped at explicit boundaries rather than with `defer`. A
`defer` in `sync()` fires at *function* exit and would have timed the whole pass while labelling it
the read phase — a measurement that lies, which is worse than none.

## A correction on widget cadence

The 16.16 notes and my summary of them described the coalescer's 120 s floor as though it were a
*rate*. It is not: it is a minimum gap, and it only decides which single moment inside a sync burst
spends a reload. The honest figures:

- **App-requested background reloads: ~43/day against a 48 cap** — about **one every 20 minutes**
  averaged over sixteen waking hours, bursty in practice.
- **Extension self-rebuilds: not capped**, requested every 10 min, and the 260906 log shows iOS
  honouring roughly one per 6 min. But these re-render the *saved snapshot* — they cannot show data
  that arrived after the last publish.
- **A logged cup: ~30 s** (water pre-empts the coalescer). **App open: immediate.**

"Every 2–10 minutes" was wrong; 480 reloads a day is not reachable under a 48 cap.

And the open question stands: **~20 minutes is not self-evidently better than the 169 s deferral it
replaced.** The bet is that fewer-but-promptly-served beats more-but-throttled. If the next log's
`reqToBuild` drops sharply, it paid; if it does not, the cap should go back up toward 66 and the
deferral is not budget-driven at all.
