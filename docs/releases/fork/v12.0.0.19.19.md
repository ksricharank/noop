# 12.0.0.19.19 (build 455) — 261019

One change on `feature/v15-widgets`. FEATURES unchanged; `store-concurrent-reads` re-stacked. It
closes two paths that started full passes outside the 19.17 RE-SCORE POLICY. Both rules are now in
the policy's doc block on `RescoreBackgroundScheduler` ("NOT A TRIGGER AT ALL").

## What the 261019-0743 log showed (first night on 19.18)

The policy itself held. Daytime syncs from 19:20 to 19:58 ran the quick pass only (`no full pass — the
quick pass found the stored nights current`). The 19:09 Refresh synced, waited, then scored once. At
06:15 the quick pass reported `the night moved for 2026-10-19`, and full passes completed at 06:36
and 06:37. Quick passes never moved Charge (`stored=` matched `wrote=` on every `kind=light`).

Two paths went around it. Since the install there were 7 completed full passes and 16 abandoned
ones; the abandoned passes cost 2,468 s of background wall time, each scoring 1 of 21 nights.

1. **Launch.** The Repository is built on the canonical id, so the launch-time read-spine adopt
   always "moves" it. `adoptActiveDevice` then forced a 21-night pass on every launch, including
   the silent background relaunches iOS makes to restore the strap connection ("Read spine
   re-pointed …", 7 launches since the install).
2. **The #899-A re-arm.** A full-pass request that arrives while a pass runs re-runs once when that
   pass ends. When the running pass was ABANDONED (backgrounded), the re-run started in the
   background at once, gave up, and re-armed again from the next sync. The 20:08 background
   relaunch began a chain of 8 between 20:08 and 22:28 (1,943 s), ended only by the sleep window.

## The fix

- **Launch adopt refreshes only.** `AppModel.adoptActiveDevice`: the first adopt of a process
  refreshes the screen with no re-score, logging `Read spine set to the active device at launch —
  screen refreshed, no re-score (261019)`. A later move (a real switch, remove or re-add) still
  re-scores. Scoring is unaffected: the engine resolves each day's owner from the registry
  (`resolveDayOwner`), not from this read id.
- **No re-arm behind an abandoned pass.** `IntelligenceEngine.analyzeRecent`: the queued request is
  dropped with `re-score: queued full pass dropped — this pass was abandoned in the background; its
  debt stays set for the next sync or foreground (261019)`. Nothing is lost: a full pass marks its
  debt when it starts and an abandoned one leaves it owed, so the next routine trigger or the
  foreground resume settles it under the policy. A queued request behind a pass that COMPLETED
  still re-runs once, as before.

## Also seen, not changed
