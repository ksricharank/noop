The cups rewrite was committed onto `release-10615-9` — a DISPOSABLE assembly — instead of onto

`release-10615-9` it flags exactly the lost commit, so this failure mode is closed rather than
remembered.

## Water: cups, priced off TODAY'S effort target

The maintainer's 260903 rule replaces the millilitre chain on every water surface:

**`target cups = baseline cups + max(effort target, effort accrued) / 10`** — "a target strain today of 50 leads to
16 + 50/10 = 21 cups". Male baseline 3700 ml = 16 cups, so effort target 50 → 21, 100 → 26, rest
day → 16. On the maintainer's own 260903 numbers (effort target 46) that is **21 cups**, where the
old millilitre path printed 16 — a 57 ml bump could not move a single cup, which is precisely the
invisibility that made the bug hard to see.

The basis is a MAX (the maintainer's refinement): the prescribed target, or the effort actually
done if that is higher. Pricing off the target alone was stable but under-asked on a day that went
harder than planned — sweat loss is real and same-day. The max keeps the goalpost honest in the one
direction that matters: within a day the ask can only GROW, never shrink, so "cups left" cannot
move backwards even when a rescore rewrites accrued strain downward. The derivation names which
side won ("today's effort target 50" vs "today's effort so far 70 … you've passed today's plan").

This also fixes the reported bug: the derivation read "yesterday's effort of 8 adds 57 ml" when
yesterday had finished at **7**. The basis had been yesterday's scored strain, which is frozen in
principle but not in fact — the 2-day light pass keeps REWRITING yesterday's row hours into today,
so the number drifted under a label claiming otherwise. Today's effort target is set once at the
morning score and describes the day being asked for: stable, and the right day.

(An earlier attempt to move this pricing inside `liveTargets` had silently not applied — the
edit's guard failed and the old anchor-based code stayed live. It is genuinely there now, so the
target and its explanation are computed together.)

Pricing in cups rather than millilitres is deliberate: the number is only ever shown, logged and
edited in cups, and the old path rounded an ml sum to 50 ml before dividing by 237 — so a one-cup
change in the ask was invisible and the derivation could not be checked by eye. It now reads
`16 + 5 = 21 cups`.

## Charge stopped flip-flopping: the light pass no longer re-judges the night

Reported: Charge — and every target priced off it — showed one value on app open, changed about a
minute later, then reverted on the next open (22 vs 47, alternating).

Recovery is a z-score against the HRV/RHR **baselines**, and on a strap-only install those
baselines are folded ENTIRELY from the nights the pass itself scored: `hist` reads the IMPORTED
device id, which is empty with no WHOOP export, so `nightlyHrvByDay` is the only source. A 2-day
light pass therefore folds a **2-night baseline**, against which a genuinely suppressed night reads
as normal — 26 ms scores **z = −1.65** against the real 21-night history (Charge 22) and **z =
+0.71** against two nights (Charge 47). Each pass overwrote the other, so the number on screen
depended on which had run last.

The light pass exists to advance today's accumulators, never to re-judge the scored night. It now
**reuses the persisted recovery** — the value the last full pass computed against the real baseline
— and only a full pass recomputes. Nil stays nil: an unscored night is never invented.

This is the third bug from one root (a 2-day window inheriting whole-history reasoning), after the
stale-eviction delete and the provenance wide-delete. The test pins the z-score arithmetic itself,
so the *reason* lives in the suite rather than only in a comment.

## The water reminder now reads the row's own goal

Reported: the notification said **2/16** while the Today row said **3/19**. Two causes, one
mistake — the reminder computing a number the row already owns:

- The **goal** came from `hydrationGoalML`, the retired millilitre formula (3700 + effort/100×700
  → 16 cups), while the row used the cups rule (→ 19). The reminder now takes its goal from the
  same `cachedLiveTargets()` the row renders, so a formula change cannot land on one surface only.
- The **drunk figure** was re-rounded to whole cups (2.5 → 2) while the row shows half-cups. It now
  renders through the row's own formatter, and the reminder's local `cups()` helper delegates to
  `HydrationGoal` instead of repeating the arithmetic.

Pinned with the reported case: 2.5 cups against a goal of 19 must read "2.5 of 19 cups — 17 to go"
and match the row's rendering of the same millilitres.

## Instrumentation for tomorrow's battery read

Counters on already-running paths, formatted only at export.

- **Retro-scan phase split.** `maxMs=592327` (9.9 minutes, with `lastMs=31`) could not be
  attributed: one wall-clock number cannot say whether the time went WAITING on the WhoopStore
  actor — contending with a re-score's throttled reads — or replaying beats. The line now carries
  `maxWait` / `maxReplay` / `maxBeats` plus `blocked=N`, a count of scans whose store wait alone
  exceeded 5 s, so one spike is distinguishable from a pattern. Maxima, not means: 140 fast scans
  would bury the outlier.
- **Pass locality.** Two full passes took 57 s and 75 s with nothing saying where they ran. Every
  pass now prints `where=background|foreground` on its trigger line — background is a battery cost
  and a suspension risk, foreground is a user waiting, and the two call for different fixes.
- **Locked BLE wakes.** puffin wakes halved (102,906 → 35,701), but a per-channel total cannot say
  whether the remainder lands while the phone is LOCKED (pure cost, no screen to read) or unlocked
  (expected). Wakes now also count under a `.locked` label; the existing per-channel lines are
  untouched.
