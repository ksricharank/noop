# 11.8.0.18.12 (build 413)

One card for the whole Trends page, charts that let you scroll past them, and one sleep-debt ledger
instead of three.

## The unified Trends card

> for the trends page, I don't like any of the widgets honestly - I just want a single new widget
> that shows trends over a range selected in the window selector that shows all the key metrics
> (this should be separately configurable) in one widget

**"All metrics"** draws the page's own window for a configurable metric set, and is the one 260920
section **shown by default** — a card meant to replace the rest of the page cannot do that while
hidden. Every per-metric block from 18.9 stays available but opt-in, so hiding the rest leaves
exactly this.

Non-interactive by construction. The scroll-capture below would be worse here, since this card is
taller than anything it replaces.

### Three styles, because each answers a different question

| Style | What it shows | What it gives up |
|---|---|---|
| **Overlay** | every metric on one axis, each scaled 0–1 against its **own** observed range | absolute values — so the legend carries current value and range |
| **Rows** | one ~38pt strip per metric, real values, own y-scale, days aligned | height |
| **Heatmap** | metrics as rows, days as columns, shaded by distance from that metric's own mean | magnitude — bands, not numbers |

The overlay is the only one that can show **co-movement** — HRV falling on the same days resting HR
rose — which separate charts structurally cannot, however many you stack.

`higherIsBetter` inverts resting HR and respiration in the heatmap. Without it a high resting-HR day
would be painted the same green as a high-HRV day, which reverses the one thing that view is for.

### Each style keeps its own metric list

> for each of the three visualizations, I want the option to independently pick the key metrics

They want genuinely different sets: an overlay is a thicket past about five lines; a heatmap costs
16pt per metric and no legibility; rows sit between. One shared list would impose the smallest of
those limits on all three. Defaults are **5 / 6 / all 9**.

Resolution is own-key → the pre-per-style key → the style default, so a wearer who had already
chosen a set inherits it once rather than finding it reset.

Switching style in the sheet **saves the outgoing style's edits first**. Flicking between styles to
compare is the natural thing to do while deciding, and would otherwise discard a selection every
time.

Deselecting the last metric is refused. A card drawing nothing reads as broken rather than as
configured, and hiding it is what Arrange is for — the sheet says so instead of letting the state be
reached.

## Charts you can scroll past

> when I scroll, I get stuck on the widget

`TrendChart` attaches `DragGesture(minimumDistance: 0)` whenever `showsHover && showsBars`. A zero
minimum distance claims the touch **on contact**, before the enclosing `ScrollView` can decide the
gesture was a scroll — so a swipe beginning over the chart scrubbed the chart instead of moving the
page.

`ScoreTrendSection` now passes `showsHover: false`, and draws **bars at every call site** (*"make the
line chart in sleep similar to this bar chart"*). No loss: the footer already prints mean, min and
max, and the calendar strip below reads individual days.

## The sleep ledger was three ledgers

The ask was for the Sleep tab's debt ledger to drive the Today sleep target *"for consistency"*. It
already did — and saying so was true and useless, because the two were computed from different
inputs:

| Surface | Credited sleep | Need |
|---|---|---|
| Sleep tab card | main sleep **+ naps** | personalized |
| Today target | main sleep only | personalized |
| Coach context | main sleep only | **flat 8 h default** |

So on any day with a nap the two screens reported different debt from the same nights, and the Today
sleep target was priced off the nap-blind figure. The comment claiming every debt surface *"keeps
the same reference"* was true of the **need** and silently false of the **sleep** — which is how it
survived.

The maintainer caught it in one line: *"but then they are not consistent"*.

`liveTargets` now takes `napSleepMinByDay` and credits naps through the **same**
`SleepDebt.creditedSleepMin` helper the Sleep tab uses, so the two cannot diverge again. Nap minutes
need `CachedSleepSession` rows that only load asynchronously while `liveTargets` is a synchronous
read, so they are derived once per refresh from sessions that refresh has **already fetched** — no
extra query — and cached like `hydrationTodayCachedML`. The parameter defaults to empty, so the
widget and Live Activity paths, which never load sessions, behave exactly as before.

The coach omitted `needHours` entirely, measuring debt against a flat 8 h inside the block whose
whole purpose is deterministic on-device figures the model is told not to recompute — it could
report a shortfall neither screen showed. Now aligned. It still cannot credit naps from that call
site (`days` carries `DailyMetric` rows with no session detail), so it **under**-credits rather than
inventing sleep — the safe direction for a figure that drives advice to rest, and stated in the code
rather than left silent.

The sleep-target explanation now **names** the Sleep tab's ledger, so the figure can be checked
against the card it comes from.
