Third fix within feature-set 14, and likely the root of every "frozen card" report that survived
`.14.1`/`.14.2`: **iOS was silently rationing our Live Activity updates.**

## The bug

NOOP declared `NSSupportsLiveActivities` but never `NSSupportsLiveActivitiesFrequentUpdates`.
Without that key, iOS gives each Live Activity a limited update budget. The unlocked live cadence
pushes every ~2 s, which spends the budget within minutes; the system then **drops updates
silently** — `Activity.update` succeeds, nothing throws, no state changes — while the card freezes.
A freshly started activity gets a fresh budget, so it ticks for a while and freezes again.

That is the 260828-1625 report verbatim ("swiped it away… worked the first couple of times, then
stopped") and the same-day "+5 frozen island while the Live tab is moving" one: the log showed the
stream armed once at 15:57:08 and untouched for 28 minutes, zero `start failed` lines, ticks
flowing — and a frozen, tilde-marked card. Every push path was healthy; the OS was discarding the
output. It also retroactively explains interminttent freezes across earlier builds that were
attributed to (real, but different) bugs fixed in `.13`–`.14.2`.

## The fix

`NSSupportsLiveActivitiesFrequentUpdates: true` in the **widget extension's** Info.plist (Apple's
documented location), mirrored in the app's. Declared via `project.yml` `info.properties` — the
extension's Info.plist is regenerated by xcodegen on every release, so a hand-edit would silently
revert (the #416 lesson).

**One new user-facing switch to know about:** the key surfaces a per-app **"More Frequent
Updates"** toggle in iOS Settings → NOOP → Live Activities. If it is ever off, the budget silently
returns. Every activity start therefore logs
`Live Activity: started — frequent updates enabled/DISABLED…` — the only witness when that toggle
is the cause of a freeze.

Verified: NOOPiOS compiled; the key present in both built Info.plists (app + appex).
