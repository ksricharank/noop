# 11.1.0.16.11 (build 323)

The expanded Dynamic Island, laid out as asked: HR / Sleep / Water on top, Effort / Steps / Cal
below, Charge gone, and nothing clipped by the corners.

**Build 322 was cut but never installed**, so this install carries both island commits — 16.10's
"HR when collapsed, the day's pairs when expanded" as well as this layout pass. 16.10's checklist
applies here too.

## The layout

Maintainer, across two messages: "get rid of charge, move sleep to top row and center hr and sleep
(right now hr and charge are getting cutoff at the corners, same with effort on the bottom left)",
then "move HR, sleep and water to top row, the other three in bottom row, with steps expanded and not
abbreviated".

    ♥ ~72        Sleep 8h05        Water 5/21
    Effort 3.2/10.7   Steps 4412/8000   Cal 605/2250

Three and three. The split reads naturally: the top row is the three figures that are NOT "how much
have I done today" — a live rate, tonight's target, and a count against a fixed daily goal — and the
bottom row the three progress pairs. Three columns per row also gives each value about a third of
the width rather than a quarter, which is what makes room for the full step count.

**Charge is removed** as instructed. It was there because its band sets today's targets, but it is a
score rather than a pair and the row reads better balanced. The FIELD is still populated on every
push: it is the decode-continuity field for an activity adopted across a build change, exactly as
`bpm` was while the HR column was away, and carrying it costs nothing. A test asserts nothing renders
it while the field survives.

**Steps were already unabbreviated here.** `stepsText` has always been the full "4412/8000"; the
"4.4k/8k" form belongs to the home-screen widget faces, where a Lock-Screen cell genuinely has no
room for two four-digit pairs. So there was nothing to change — but a test now pins it, because the
two forms live one file apart and a later tidy-up "unifying" them would silently abbreviate the
island.

## The corner clipping

This was a real constraint of the expanded presentation, not a styling slip. It wraps the sensor
cutout, and its leading/trailing regions run into the rounded corners, so content pinned to an outer
edge is cut by the curve. Both halves of the fix are needed and either alone leaves the report
standing:

  * **centre** each region's content (`maxWidth: .infinity`) rather than letting it sit against an
    edge, and
  * **inset** the outer edge off the curve.

The bottom row had the same problem for the same reason — it used `Spacer()` between columns, which
pushes the first and last hard against the region's edges. That is the "effort on the bottom left"
half. It is now evenly-divided equal shares, each value centred in its own third.

`statColumn` also gained a shrink step. Its `fixedSize()` stopped a value being squeezed narrow
enough to wrap mid-number, but with equal columns a wide pair can want more than its share and would
overflow into a neighbour or the corner; it now narrows to fit. `fixedSize` is kept on the VERTICAL
axis only, which is what that fix (#759) was actually about.

**A first cut of the top row put Sleep in the `.center` region.** That region sits directly under the
sensor cutout and is the narrowest of the three top slots, so it risked reproducing the exact bug
being fixed. The top row is instead built from leading + trailing, each holding an evenly-divided
half, and a test now pins `.center` out of use.
