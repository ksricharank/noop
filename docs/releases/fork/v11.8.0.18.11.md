# 11.8.0.18.11 (build 412)

The Key Metrics merge, finally in the right file and with the right semantics. Two mistakes, both
found by the maintainer on the device, both worth recording because neither was a coding error —
they were a wrong file and a wrong reading of the request.

Supersedes 18.10 (build 411), which carried the first half of this fix.

## Mistake 1: the change shipped into a view the phone never renders

18.9 merged "Your cards" into KEY METRICS in `Strand/Screens/TodayView.swift` — the **classic**
Today. iOS renders `Strand/Liquid/LiquidTodayView.swift`, a separate implementation with its own
`keyMetricsSection` and `yourCardsSection`.

The change compiled, passed its tests, cut a build, and did nothing. The maintainer: *"I don't see
the key metrics and your cards sections combined? what gives?"*

**The evidence was in the first screenshot.** It reads "7-day trend". The classic header hardcodes
`"14-day trend"`; only the liquid view computes that label from a window. One `grep` for the string
would have named the right file immediately, and it was on screen the whole time.

`Strand/Liquid/` holds only `LiquidTodayView` and `LiveSessionView` — Trends, Sleep and Recap have
no liquid twin, so the per-metric blocks, the tap gate and the digest cadence from 18.9 were always
in the right place. Today is the one screen with two implementations.

## Mistake 2: "one section" meant one BLOCK, not one hideable unit

The fix in 18.10 nested the dashboard rows inside `keyMetricsSection`. The maintainer, immediately:

> cards are now under the daily trends section - when I remove daily trends, I lose the cards as
> well which makes no sense

Exactly right. Hiding the tile grid deleted Stress, Fitness Age, Vitality and VO₂ Max along with it,
and neither half could be hidden without the other. The request was for a tidier page; the result
was strictly fewer controls than before.

`.yourCards` is its own section again — independently movable and hideable — and renders *without* a
second full header:

- **Directly after Key Metrics:** a hairline divider and a quiet "CARDS" sub-head. The two read as
  one block.
- **Anywhere else, or with Key Metrics hidden:** a full "YOUR CARDS" header returns, because a bare
  divider under an unrelated section reads as a rendering fault rather than as a continuation.

One block visually, two sections structurally.

Three things the liquid view's own code forced, each a silent regression if missed: `sectionHead`
takes a non-optional `String`; the row builder there is `liquidCard(for:)`, not the classic
`dashboardCardRow`; and the hydration and coach filters had to come along, or a card the wearer had
switched off would have reappeared.

## The HealthSyncPolicy.swift error, correctly diagnosed

Twice today a build failed with:

> Build input file cannot be found: '…/Strand/Data/HealthSyncPolicy.swift'

It was diagnosed the first time as a stale Xcode build cache, which cost the maintainer a
DerivedData wipe for nothing. **That was wrong.** The file genuinely does not exist on
`feature/v15-widgets` — it comes from another feature branch that only the release assembly merges
in — and the generated project had been written while the **release** branch was checked out.

It is the `xcodegen generate` after every branch switch rule in `CLAUDE.local.md`, skipped. One
command settles it, and should be the first thing run next time this appears:

```
grep -c HealthSyncPolicy Strand.xcodeproj/project.pbxproj
```

`10` on the release branch, `0` after regenerating on the feature branch. A missing-input error
whose file is present on disk means the PROJECT is from another branch, not that the cache is stale.

Related: each worktree path gets its own DerivedData hash, so several `Strand-*` folders accumulate
and `open -a Xcode` can front a window belonging to a different worktree. Open by absolute path, and
read the version from `Strand.xcodeproj/project.pbxproj` rather than `project.yml` — that is what
Xcode will actually build.

## Verification

Both app targets compile, built into an isolated `-derivedDataPath` so a verification build cannot
disturb an open Xcode session — which is what produced the confusion above.

**Not verified on device.** Every claim in this file about layout is a claim about what the code
draws, and this build exists because two such claims were wrong in a row.
