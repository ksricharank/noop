# Fork build 10.6.0.9

**Base:** upstream [`v10.6.0`](https://github.com/ryanbr/noop/releases/tag/v10.6.0) staging line ·
**Build:** 259 · **Date:** 27 August 2026 · **Platform:** iOS (sideload)

Second same-day fix build. The 10.6.0.8 duty cycle's STATE MACHINE was proved correct in the
260827-2142 log (lock → toggle 0 + 0x2A37 unsubscribed with hardware confirmation; unlock →
re-subscribed within a second) — but a rapid lock/unlock test showed both EDGES were mushy: live
pushes kept repainting the LOCKED Lock Screen for up to a minute after locking, and freezes lagged
unpredictably.

## The cause: the keybag is not the lock

Every consumer read the lock from `isProtectedDataAvailable`, and iOS flips that keybag **10–60 s
after** the physical lock. For that whole grace window the code genuinely believed the phone was
unlocked — gate open, stream armed (the +15 s reconcile then waited out a keybag that had not
flipped yet either). Meanwhile the same log showed the crisp signal was already in hand:
`protectedDataWillBecomeUnavailable` fired at 21:39:57, the instant of the lock — but was only
feeding a log line.

## The fix: `DeviceLockState` — latch at the notification, keybag as backstop

`locked = keybag unavailable OR latch fresh (< 30 s TTL)`, read by all three consumers: the stream
reconciler, the Live Activity's live-tick gate, and the offload-driven data refresh's guard.

- **Lock edge:** freeze and stream-silence begin at the notification (~instant). The keybag flip and
  the 15 s / 60 s reconciles remain as backstops.
- **Unlock edge:** `DidBecomeAvailable` and `didBecomeActive` clear the latch before reconciling —
  as crisp as the lock edge. The latch also clears regardless of duty mode, so a Settings flip
  mid-latch cannot strand it.
- **The stale-latch hole** (lock latched → app suspends → unlock missed): a latch older than its TTL
  with an OPEN keybag yields to the keybag, so a missed unlock cannot freeze an unlocked phone for
  more than ~30 s.

Also in this build: the `BLE wakes:` header line fix (`feature/battery-instrumentation`) — the
counting window was anchored on a lazy static first touched *inside* the export, microseconds after
the `now` it was compared against, so the line silently vanished from every process's FIRST export
(the 2142 log printed the CPU sibling but not this one). Anchored on the first recorded
notification now; zero-second windows floor to 1 s instead of dropping.

## Expected behavior after this build

- Lock the phone → the Lock Screen number freezes within ~a second and then changes ONLY when a
  sync lands (~15 min), showing that window's average + last recovery/effort.
- Unlock → live within a few seconds *when the app process is running*. Honest limits that remain:
  a SUSPENDED app cannot see an unlock until its next BLE wake (opening the app is always instant),
  and ActivityKit may defer a burst of background updates after rapid-fire toggling — both are
  measurement targets, not code bugs.
