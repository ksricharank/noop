# Fork release 11.1.0.16.1 (build 313)

Development-machine quiet. The macOS app no longer starts a Bluetooth client or registers with the
location daemon just because it was built. No iPhone-facing behaviour changes.

## The complaint

Building the project launched the macOS app, which fired a burst of Bluetooth requests — and
location requests alongside them. On a fork deployed to an iPhone, that is radio traffic and OS
permission prompts generated by the act of building.

## Why the macOS target cannot simply be turned off

It **hosts `StrandTests`**. Its `TEST_HOST` / `BUNDLE_LOADER` point at `NOOP Staging.app`, and the
suite links against that module via `@testable import Strand`. Removing or disabling the target
takes all 1669 app-level tests with it — including the ones that caught the coach-merge regression
and the light-pass eviction bug. That is a bad trade for silencing a prompt.

The target is also not what the iOS scheme builds: `NOOPiOS`'s only buildable is `NOOPiOS.app`. The
noise came from the **Strand scheme being the selected one**, whose buildables are the macOS app
plus the tests — so Cmd-B built it and Cmd-R launched it.

So the fix is to the app's launch behaviour, not to the build graph.

## Two independent causes, both fixed

**Bluetooth.** `connectFromSystem` is now gated on macOS behind an opt-in flag that defaults to
absent — i.e. idle. That is the path which fires *without anyone asking*: at launch, and on every
Bluetooth toggle or `bluetoothd` restart.

Scoped to the system path deliberately. The user-initiated `connect()` — the Connect button, the
scan flow, Add-a-WHOOP — is untouched, so the macOS app stays fully usable and simply waits to be
asked. Gating both would turn "idle until asked" into "broken", which a test now pins. iOS is
explicitly excluded: there, auto-connect on radio-on IS the product.

    defaults write <bundle-id> noop.macos.autoConnect -bool YES   # opt back in

**Location.** `AppModel` builds `GpsWorkoutRecorder` eagerly at launch, and the recorder held its
`CLLocationManager` in a STORED property whose delegate was assigned in `init` — which registers the
process with the location daemon there and then. Nothing was *requesting authorization* at launch
(`requestWhenInUseAuthorization` is only reached from `start(...)`); mere construction was enough.

The manager is now lazy, with the configuration that ran in `init` moved into its lazy initializer
so it still happens before any caller can observe it. Not platform-gated, unlike the BLE change:
building a location manager before it is needed is wasted work on iOS too, and iOS behaviour is
unchanged because a workout is still what forces it.

The macOS `NSLocationWhenInUseUsageDescription` stays — the macOS app can still record a GPS workout
if asked, and removing the string would make that path crash rather than prompt.

## Verification

- `Strand` (macOS) and `NOOPiOS` both **BUILD SUCCEEDED**.
- `StrandTests`: 1669 tests, only the known timezone-sensitive `SkinTempAbsoluteDisplayTests` flake.
- The BLE gate's test was confirmed to **FAIL when the gate is defeated**, rather than merely
  passing as written.

These are structural tests: they read the source, because the property is about which code path a
call sits on. A behavioural test cannot reach here — instantiating the objects to prove the negative
is the very thing under test.

**What this does NOT verify:** that the prompts are actually gone on the machine. That is observable
only by building and running, which is the next thing to do. Everything carried from 16.0 and
15.19–15.21 remains hardware-unverified: the notification "Add a cup" action, water on the widget
faces, and both buzz fixes.

Before installing: clear the stale provisioning profiles —

    rm -f ~/Library/Developer/Xcode/UserData/Provisioning\ Profiles/*.mobileprovision
