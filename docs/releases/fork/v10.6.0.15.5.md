# Fork release 10.6.0.15.5 (build 295)

One real bug fix and two maintainer-requested features, from the 260902 evening report.

## The target reversion — a light pass was DELETING the last scored night

Reported: targets that were right all morning silently reverted (Charge showing an implausible
old value, steps + sleep targets re-priced), then repaired themselves about a minute later. Two
screenshots a minute apart showed Charge 91 / steps 8000 / sleep 9h15 flipping to Charge 13 /
steps 4000 / sleep 9h55.

Cause, introduced with the light pass the day before (`feature/v15-battery`): the end of
`analyzeRecent` runs a window-wide STALE EVICTION — "delete every computed day in
[oldestDay, newestDay] this pass did not reproduce". That reasoning is sound only for the full
21-day pass, which re-derives its whole window. The light pass runs at `maxDays: 2`, so it was
applying that reconciliation to yesterday+today every ~10 minutes and deleting the last scored
night whenever it could not re-derive it from a 2-day raw read. The destroyed row took the
widget/Today anchor with it (`widgetAnchor` then carries the freshest STRICTLY-PRIOR scored day),
so Charge/Rest read unscored and every target re-priced off an arbitrarily old row until the next
full pass restored it. `persistComputedScores`' provenance wide-delete had the same over-reach.

Fix: a light pass is now strictly additive — no eviction, and its provenance rewrite is bounded to
the days it actually scored. The full pass still reconciles the whole window at the morning open.
Pinned by `LightPassNonDestructiveTests` (both write-scope bounds, plus the anchor consequence).

Note: the `7/0` effort target visible in both screenshots was a SYMPTOM of the same bug — an
unscored anchor yields no session prescription. Rows already damaged on-device correct themselves
at the next full pass, not instantly on install.

## Pace-check titles written by the coach

The notification keeps its three `actual/pace/goal` rows, but the title is now generated per
check-in and scaled to the size of the gap — a quick walk when slightly behind, a real block of
time when badly behind. One short call (~every 2 h by default) carrying only the deficit ratios,
no history. ANY failure — no provider, no consent, timeout, empty or over-long reply — falls back
to the static "Behind pace", so the notification never waits on the network.

(The two-row notification in the report was not truncation: Effort was `7/0`, and a zero target is
skipped by design. With the anchor bug fixed, a real effort target restores the third row.)

## Water reminders — on the EXISTING hydration tracker

Wired into the hydration feature already in the tree, never a second tracker: the cups counted,
the goal measured against and the log the action writes to are the tracker's own.

- Two settings directly under **Settings → Features → Hydration tracking**: a start time and an
  interval (1 / 1.5 / 2 / 2.5 / 3 hours). Reminders stop after 10pm.
- The notification states today's cup goal, cups drunk and cups left, in ROUNDED cups. The daily
  cup goal stays DERIVED (`HydrationGoal` prices it off profile + today's effort) — a second
  hand-set number would disagree with the Today card the moment effort moved.
- **Long-press the banner (or swipe and tap)** for "Logged a cup", which writes through
  `Repository.logHydration` — the same call the +Cup button makes — without opening the app.
  **Tapping the body** opens NOOP; iOS reserves that gesture and it cannot be reassigned.
  **Ignoring it logs nothing** — iOS never reports a dismissal, which is the wanted behaviour.
