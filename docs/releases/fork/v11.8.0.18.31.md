# 11.8.0.18.31 (build 432)

The root cause, fixed at its chokepoint: a starved background never grinds a pass inline.

## The root cause (the durable record — read this before the next uplift)

**What broke:** upstream v11.8.0's #2296 deleted the old "defer heavy passes out of the
background" policy and replaced it with CPU pacing — passes now RUN through background windows.
**What it collided with:** iOS 27 polices sustained background CPU adaptively, starving the
process progressively.

**The evidence chain, all from the wearer's log archive:**
- Controlled comparison (same phone/strap): background light passes ran 8–30 s for three weeks —
  *including on iOS 27 with the pre-uplift 11.6 app (260919)*. The first 1000-s pass appears with
  the uplift (260920), then 384 → 879 → 2272 → **8360 s**, worsening daily as the OS clamps harder.
- Direct starvation measurement (260929): one-night pass, `read=4187ms compute=585833ms` — 585 s
  of wall for ~5 s of work. CPU, not I/O.
- Foreground never exceeded ~110 ms/statement all week; background medians ran 100× worse — and
  same-process HealthKit calls starved identically, which no app-level cause can produce.
- Ruled out with measurements: WAL starvation (1 MB), DB size (foreground fast on the same 1.7 GB
  file; the six 3.6M-row 1 Hz tables are a multiplier, and a later retention conversation),
  the fork's own features (pre-uplift fine), Health write-back volume (a downstream symptom).
- Collateral mechanism: all store reads funnel through one actor, so screens (the "Recap took
  forever" report) queue behind a starved background read.

## The fix

ONE chokepoint in `analyzeRecent`, after the fingerprint gates (so unchanged-skips stay free),
covering every entry — the post-offload path, the completion re-arm, the light pass, direct calls:

- A **50 ms CPU canary** (`BackgroundCPUCanary`, run at `.utility`, the passes' own QoS) measures
  actual starvation. Bounded: a fully-starved probe gives up at 5 s wall and reports the factor.
- **≥×4** (`RescoreBackgroundPolicy.backgroundStarvationFactor`): the pass does not start inline.
  A full pass records its debt and arms the granted `BGProcessingTask` window — where iOS provides
  real CPU — and a light pass waits for a granted window or foreground. Ledger:
  `re-score: skipped before starting — background CPU starved (canary: 50 ms of CPU took N ms, ×F)`.
- **<×4**: background behaves exactly as before (×1.5–4 logs itself and proceeds).
- Every granted-window settle now logs `granted-window canary ×F` — the number that proves the
  posture works, and the tripwire if iOS ever tightens granted windows too.
- macOS: unaffected by construction (never backgrounded).

## Upstream-breakage insurance (deliberately layered)

1. `BackgroundStarvationGateTests` (3) pins the threshold, the probe and the counted cause — a
   deleted gate is a red test, not a week of 8000-second passes.
2. The root-cause essay lives ON the policy constant and at the engine gate, where a merge
   conflict forces a human to read it.
3. `cpu-starved` renders in the header's `Re-score dropped:` tally.
4. This note. If, after a future uplift, logs again show multi-hundred-second light passes with
   multi-second `store sql` statements only in background: re-apply this gate first, argue later.

## Upstream issue draft (ready to file)

> **iOS 27: #2296's background pacing collides with adaptive background-CPU starvation**
> On iOS 27, sustained background CPU causes progressive starvation of background-QoS threads
> (measured: 50 ms of thread CPU taking 5+ s of wall; a one-night scoring pass spending 585 s of
> wall on ~5 s of compute). Since #2296 replaced background deferral with pacing, heavy passes now
> run in exactly these windows: pass wall times grew from ≤30 s to 8000+ s over a week on a
> device upgraded to iOS 27, store reads (which decode rows on-thread) stretched 100×, UI reads
> queued behind them on the store actor, and HealthKit calls in the same process starved
> identically. Foreground was unaffected throughout. Suggested direction: gate inline background
> passes on a measured CPU canary and fall back to BGProcessingTask windows (which receive normal
> scheduling); we run this as a fork patch with the threshold at wall/cpu ≥ 4.
