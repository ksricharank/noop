# 11.1.0.16.4 (build 316)

Configurable delivery windows for both nudge schedules, the water reminder moved to Automations,
and the two real causes of "my notification titles are all the static fallback".

The FEATURES set is unchanged; this is 16.4 rather than 17.0 because nothing was added to or
removed from the stack.

## Reminder scheduling: start, stop and gap for water and pacing

Maintainer request: "I want a start and stop time control and the duration of the gap in between
for both pacing, and for water."

Before this build only two notifications were clock-scheduled at all — the water reminder (start +
interval, with a HARDCODED 22:00 last slot) and the wind-down nudge (computed from wake minus sleep
need minus lead). The morning brief had a "not before" floor and pacing had an interval only. The
rest (breathe, illness, strain target, battery) are event-driven and have no time to configure.

**Water.** The 22:00 ceiling becomes a real `stopMinute`, and its DEFAULT is the start of the sleep
window — the shared `notif.quietStartMinutes` that quiet hours, the inactivity detector and the
overnight BLE gate already read. This is what the maintainer asked for ("keep it to the configured
stop time I have in the UI"): the wearer already tells NOOP when their night starts, so a reminder
to drink ends when the waking day does, with no second number to keep in sync. Moving the sleep
window moves the last reminder. Behaviour-preserving on an existing install, since that window's
default IS 22:00.

`lastSlotMinute` survives, but ONLY as the retirement grid's bound: the pre-260903 repeating
calendar-request ids were minted against 22:00, so the sweep that cancels them must keep spanning
exactly that range. A test pins this, because it is the kind of constant a later cleanup would
"simplify" and thereby orphan those legacy requests forever.

**Pacing.** Start and stop are a FLOOR AND CEILING ON DELIVERY, deliberately not a replacement for
the wake anchor. This was put to the maintainer as an explicit choice and they picked it.

The reason matters: `dayStartMinute` does two jobs — it begins the checkpoint grid AND is the
denominator of the pace math ("how far through my waking day am I?"). Repointing it at a clock time
would silently reprice every target on an early or late morning, the exact mispricing the wake
anchor exists to prevent. So the grid and the proration keep using the real wake; the two new
numbers only decide which of the resulting checkpoints may speak. A test asserts the windowed and
unbounded nudges are byte-identical at the same moment, which is the property a future refactor
could quietly lose.

A muted checkpoint is CONSUMED, not banked, so silencing the early edge cannot queue a nudge that
fires the instant the floor opens. Both bounds are optional; unset means unbounded, i.e. the
pre-change behaviour.

## Notification titles: two independent causes, both from the 1119 log

The maintainer's own observation is what cracked this: the coach works on the synthesis page and in
Ask-coach, so the provider and key are fine and the fault must be specific to the title path. The
260903 instrumentation then named both causes outright.

**1. The prompt fought its own validator.**

    title — reply rejected (parroted example, too long, or empty): Time to block out an hour

"Time to block out an hour" is on the REJECTED canned-lines list, and the prompt was offering it
verbatim as an example. A model that followed the instruction was guaranteed the static fallback.
The rejection was correct for the 260903 bug (every nudge arriving as a verbatim example) but by now
it was discarding a reasonable answer to a genuinely large gap — worse than the parroting it caught.
Fixed upstream of the check: the prompt DESCRIBES the shape rather than supplying quotable text. The
list stays as a backstop. A new test asserts the prompt quotes none of the rejected lines, and was
verified to FAIL against the old prompt, naming all three.

**2. A coach-sized timeout on a background path.**

    Automation: pace-check title — request failed: The model took too long
    re-score (light): done — scored 2 night(s) in 25140 ms      <- the line immediately before

Titles are requested from the post-offload path, competing with a 25-second re-score and a
just-finished backfill; the synthesis and Ask-coach run while the wearer is in the app with nothing
else going on. That is exactly why the coach screen looked healthy while every notification fell
back. 180 s is right for a user-initiated answer with a visible Thinking state and wrong here — the
nudge already carries a correct static title, so a long wait can win nothing on a battery-sensitive
path. Titles now use their own 20 s session (a between-bytes stall budget, so a model answering
steadily is not cut off).

## An overstated diagnostic, corrected

The same log showed all four nudge buzzes logging "acked" while the strap's own replies were
`RUN_HAPTIC_PATTERN_MAVERICK → PENDING(2)` and `RUN_ALARM → FAILURE(0)` — against a standing report
that the buzz is not always felt. "acked" meant only that the BLE stack acknowledged the write; it
said nothing about the strap accepting the command or the motor running. That is the failure mode
CLAUDE.md warns about (a diagnostic may only assert what it can attribute), and it is plausibly why
the buzz complaint has been hard to pin down.

Now logs "written" and points at the command responses, which arrive asynchronously and were already
being logged. NO behaviour change — the buzz path itself is untouched. Whether those PENDING/FAILURE
replies mean the motor stayed silent is an open question for the next log.

## A test I had written wrong

`HydrationConcurrentLogTests` derived its day from `pid % 100`, which recycles, so a re-run
eventually reused a year and collided. The UserDefaults entry list is cleared in `setUp` but the
SQLite series row was not, so a second run added to the first run's banked total: 1416 against an
expected 708, EXACTLY double.

Worth recording because it looked exactly like the lost-write bug it guards, and is its opposite: a
lost write makes the series LOWER, never higher, and doubling is the signature of a surviving row,
not of a race. Both records of the day are now zeroed in `setUp`, through the ordinary upsert path
rather than a test-only hook. Verified by running the suite three times consecutively, where the
second run used to fail.

## What the next install must show

1. **Notification titles are model-written.** The strap log's `title —` lines should read
   `written by <model>` rather than `request failed` or `reply rejected`. This is the primary thing
   to check: two independent causes were fixed, and the log names the reason on every attempt, so a
   remaining failure is self-diagnosing.
2. **Water reminders honour the new stop.** Reminders should end at the sleep-window start (or an
   explicit stop), and `water reminder posted (slot …)` should show no slot past it.
3. **Pacing respects its window** when one is set, and — the subtler property — the nudge BODIES
   should be unchanged from an unbounded day, since the window must not reprice the pace math.
4. **Day-quality scores one day per pass** now that the backfill is done: `day-quality: scored 1
   day(s)` rather than 20.
5. **The buzz question, with an honest log.** `Buzz: one-shot written` followed by the real command
   responses. If those are still PENDING/FAILURE while no buzz is felt, that is now clean evidence
   pointing at the command path rather than at the write.

Still unverified from earlier builds: the notification "Add a cup" action, water on the widget
faces, and the macOS idle-at-launch change.
