# Fork build 10.6.0.10

**Base:** upstream [`v10.6.0`](https://github.com/ryanbr/noop/releases/tag/v10.6.0) staging line ·
**Build:** 260 · **Date:** 27 August 2026 · **Platform:** iOS (sideload)

Two changes over `.9`, both from its first hardware pass (which otherwise CONFIRMED the latch
build: island live when unlocked, Lock Screen static when locked — verified on device).

**1. The lock-edge repaint (`feature/locked-stream-duty-cycle`).** The frozen number was whatever
the last LIVE tick pushed a beat before locking (the last island value), held until the next sync
repainted it up to a full cadence later — nothing painted the promised window average AT the lock.
Now, on `protectedDataWillBecomeUnavailable`, the app latches (idempotent — observer ordering with
BLEManager's is unspecified, and the refresh's own guard reads the latch) and invokes the same
`lockedActivityRefresh` path the offload hook uses. The live path persists its samples continuously,
so the store answers the window average at the lock rather than as-of the last sync. Locked display
is the average from its first second; live values appear only while genuinely live.

**2. The averaging window is now a parameter.** ANY negative Lock-Screen refresh opts into the duty
cycle; its magnitude is the window: `-20` = a 20-minute average (clamped 1–240). `-1` stays AUTO —
the window matches the sync cadence (15 min; 60 in low-refresh) so each repaint summarizes exactly
the span since the last one; that remains the recommendation. The repaint MOMENTS are data-driven in
every case (once per completed sync, plus the lock edge) — the parameter only chooses the smoothing:
wider than the cadence = slower, overlapping averages; narrower = "the last N minutes as of this
sync", with the rest of the inter-sync span unshown. The freshness (stale) window is therefore based
on the sync cadence, never the averaging window. Recovery ("charge") and effort on the locked card
are the last SCORED values from the shared widget anchor, refreshed at every repaint.

Also learned this evening, operationally (belongs in FORK-RELEASE): **the main checkout's `release`
branch and multiple open Xcode windows are an install trap.** A ▶ pressed in a window on the stale
main checkout installed 10.6.0.6 — a build with no duty cycle and whose 0-clamped leftover `-1`
setting meant fully-live locked pushes — which read as "the fix made things worse". The build on the
phone must be verified (the app's own version display / log header `App:` line) before judging any
behavior; keep ONE Xcode window open, and keep the main checkout's `release` reset to the current
assembly.
