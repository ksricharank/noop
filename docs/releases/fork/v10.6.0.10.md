# Fork build 10.6.0.10

**Base:** upstream [`v10.6.0`](https://github.com/ryanbr/noop/releases/tag/v10.6.0) staging line ·
**Build:** 260 · **Date:** 27 August 2026 · **Platform:** iOS (sideload)

One change over `.9`, from its first hardware pass. The latch build works — island live when
unlocked, Lock Screen static when locked — but the frozen number was whatever the last LIVE tick
pushed a beat before locking (the last island value), held until the next sync repainted it up to a
full cadence later. Nothing painted the promised window average AT the lock edge.

**Fix (`feature/locked-stream-duty-cycle`):** on `protectedDataWillBecomeUnavailable`, latch
(idempotent — observer ordering with BLEManager's is unspecified, and the refresh's own guard reads
the latch) and invoke the same `lockedActivityRefresh` path the offload hook uses. The live path
persists its samples continuously, so the store answers the 15/60-minute average at the lock rather
than as-of the last sync. Locked display is now the average from its first second; live values
appear only while genuinely live.

Also learned this evening, operationally (belongs in FORK-RELEASE): **the main checkout's `release`
branch and multiple open Xcode windows are an install trap.** A ▶ pressed in a window on the stale
main checkout installed 10.6.0.6 — a build with no duty cycle and whose 0-clamped leftover `-1`
setting meant fully-live locked pushes — which read as "the fix made things worse". The build on the
phone must be verified (the app's own version display / log header `App:` line) before judging any
behavior; keep ONE Xcode window open, and keep the main checkout's `release` reset to the current
assembly.
