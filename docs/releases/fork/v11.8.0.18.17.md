# 11.8.0.18.17 (build 418)

The Charge flip, actually. Two bugs — one upstream's, one ours — that compound, found by the
ledgers 18.16 shipped.

## Bug 1 (ours): an abandoned pass deleted twenty days of computed history

The 260906 abort gate breaks the day loop when the app is backgrounded. Everything after it kept
running as a full pass. Two of those steps are window-wide:

- **Stale eviction** — deletes every computed row in `[oldestDay, newestDay]` this pass did not
  reproduce. `oldestDay` is the whole 21-day window regardless of where the scan stopped, so a
  pass abandoned after night 1 deleted the other twenty. The 260921-0740 log shows this **four
  times in one morning** (`ABANDONED after 1/21` ×4).
- **Provenance / metric-series wide-delete** in `persistComputedScores` over the same span.

The 260902 light-pass guard already described this exact failure and gated it on `lightPass`. The
abort gate opened a second route the flag cannot see. Every post-scan gate now reads
`partialBaseline` (light OR abandoned): the persist window is bounded to the scanned days, rest
points and the weekly stages are skipped, and the eviction does not run. A partial pass can
rewrite what it produced and nothing else.

Why the number was 36: with Sep 12–20 evicted and today nil, `widgetAnchor` fell back to the
oldest scored row that sits *outside* the window and so is immune to eviction — **18 August**.
Then the foreground pass restored the window and today read 62. Not one-time: every abandoned
background pass repeated it.

## Bug 2 (upstream, taken by the v17 uplift): pre-labelling R-R became unscorable

Upstream #2046 (v11.6.0, "Correct WHOOP 5 R-R interval units") reads a confirmed WHOOP 5's R-R
through a single labelled transport: `srcChannel IN (5, 7)`. Rows banked before labelling began
carry NULL and are excluded — *"remain stored but cannot be … spliced into a scored beat train"*.
HR and motion are untouched, so those nights stage sleep, score RHR and effort, and have no HRV
and no Charge. On this install the boundary is exact: Sep 12 onward has R-R, nothing before does.

Upstream's repair, #2115 ("Preserve legacy WHOOP 5 HRV and Recovery across re-score"), landed
two days later — in v11.8.0. The fork ran v11.6.0 from 11 to 19 September, and in those eight
days every full pass overwrote the stored HRV/Charge for Aug 19–Sep 11 with nil. #2115 preserves
only a stored row that still holds a value; by the time it arrived there were none. The v17 uplift
notes assessed #2046 as *"Zero fork contact"* — true of the code, wrong about the data.

**This build does not relabel the legacy rows.** The maintainer's instruction was forward-looking
only; the rows are intact on disk and a one-time, tested relabel remains possible. The window
heals itself as it slides: in eleven more nights every night in it is post-#2046 and the baseline
reaches 21 on its own.

## Two more ledgers

- **`evict: removed N stale computed day(s)`** — always-on, prints only when N > 0. A delete of
  computed history is never silent again.
- **`legacyScores preserved=X hrvMissingWithSleep=Y of N day(s)`** — once per completed pass.
  `preserved` is what #2115 carried forward; `hrvMissingWithSleep` is nights that staged sleep,
  scored no HRV and had nothing stored to preserve. Deliberately not attributed to a cause (a
  strap on the charger reads the same); it is the number that must only ever fall.
- `chargePublish` now carries `battery=` too — the widget stopped showing battery on a build where
  the path is intact, so the next log says what each publish actually carried.

## Verification

Both app targets compile. `AbandonedPassBaselineTests` grows to 9 (eviction predicate, persist
window, both directions); `LightPassNonDestructiveTests` (8) still pass. Full macOS suite: only the
4 pre-existing failures.

## What the next log must show

- **`legacyScores … hrvMissingWithSleep=` falling by one per day** until it reads 0 around
