# 11.8.0.18.9 (build 410)

Four asks from the 18.8 install, one of which could not be built as stated.

## Per-metric trend blocks — so Daily signals can be retired

The maintainer's framing was the useful part: *"if I have these, I can retire the laggy daily trends
widget."*

Seven new arrangeable Trends cards — **HRV, Resting HR, Day quality, Sleep, Effort, Water,
Respiratory** — each a full `ScoreTrendSection`: window selector, chart, comparison footer, calendar
strip. The same component the Sleep and Recap tabs already use, pointed at a different series.

Each carries **its own window**, which is the thing the shared range bar cannot express: HRV over 90
days while sleep sits at 14.

The point is not that seven blocks are cheaper than one card — they are not. It is that they are
**independently hideable**, so the page costs the metrics actually being read. `smallMultiples`
renders five charts in one body whether or not all five are wanted.

All seven are hidden until switched on in Arrange, so an untouched install renders exactly the
pre-18.9 page.

### The bug the layout tests caught

Keeping the new cards out of `defaultOrder` (so they would not appear uninvited) also kept them out
of `decodeOrder`'s append loop, which reads from that same array. They would have been **invisible
on the page and unreachable in the Arrange sheet** — present in the enum, impossible to enable.

`TrendsLayoutPrefsTests` is written against exactly that failure:

> a wearer upgrading and finding a section has silently vanished from both the page AND the Arrange
> sheet

Existence and visibility are now separate concerns: `canonicalOrder` (every card, in a written-out
deterministic order — not `allCases`, whose order is source order and nobody's contract) drives
decode; `defaultHidden` drives what renders. Both the page and the sheet read one `effectiveHidden`,
because seeding the sheet from the raw stored set listed all seven as "Shown" while the page hid
them.

## One Key Metrics section

The dashboard rows now sit under the tile grid inside KEY METRICS, behind a divider with a small
"Cards" label and their own Edit — two unlabelled Edit buttons in one section would be ambiguous.

They stay **rows**. Stress, Fitness Age, VO₂ Max and Vitality have no tile form, and Coupled and
Coach carry no value at all — they are navigation. Converting everything to tiles would mean
dropping the last two and inventing tiles for the others, losing the tap-through that is the whole
point of a dashboard row.

The `yourCards` section case is **kept, rendering nothing**, rather than deleted: removing the
rawValue would make every stored layout containing it decode short, and the recovery rule appends
missing cards — it cannot restore an order it never saw.

## A tap gesture that survives a clap — and what could not be built

The report: *"when I clap my hands, it still logs a water by accident"*, with the ask being a custom
pattern — two taps, a gap, two taps, the gap configurable.

**That is not expressible, and the reason is worth recording so it is not re-attempted.** The
double-tap is detected in WHOOP's own firmware, which sends NOOP a single event meaning "a
double-tap happened". The app never sees individual taps, their spacing, or how many there were. A
custom inter-tap pattern would need firmware, which `AGENTS.md` bars outright.

What IS expressible is the same idea one level up: require **N double-tap events inside a window**.
A clap produces one event and is ignored. A deliberate tap-tap / pause / tap-tap produces two and
fires. The accidental trigger now has to happen twice in a row to cost anything.

Automations gains **"Taps needed"** (1–3, default **1** = the previous behaviour exactly) and
**"Within"** (1–10 s, default 3).

**Ordering matters, and is commented at the call site.** This gate runs BEFORE the existing
separate-taps debounce, because the two guards want opposite things from a closely-spaced second
event: the debounce exists to swallow it, and a multi-event gesture is built out of exactly that.
Debounce first and the second half of every gesture is rejected, so the count can never be reached.

## Digest cadence

Integration gains **"How often"**: 24 h down to 1 h, labelled `6 h — 4× a day` because "6" alone
does not say whether it means six writes or six hours.

Only divisors of 24 are offered, so writes land at the same clock times every day rather than
walking around it. Slots anchor on the wake hour, and the rule walks **back** to the previous slot
when `now` is before it — without that a 6-hourly cadence went silent from midnight to the anchor
every single day.

That also corrects a fault the old test had pinned as correct: a never-written file before the
anchor hour now writes instead of idling until the hour comes round.

## Verification

Both app targets compile. 2456 macOS tests, with only the two pre-existing
`SkinTempAbsoluteDisplay` / `SleepCarriedStamp` failures already confirmed on a clean v11.8.0
worktree.

which is the case that would make the setting useless for the wearer it exists for — and the
cadence, including the before-the-anchor-hour slot.
