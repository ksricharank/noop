# 11.1.0.16.17 (build 329)

The re-score battery cost, fixed at its actual source. One pass was 82 % of it.

## What the attribution showed

The 16.13 instrumentation's first full-day read:

    Re-score today: 73/76 done, 96 dropped — cpu bg=6946s fg=1706s · longest 4214s (forced)
    Re-score by trigger: light-today 57/58  post-offload 3/3  forced 13/15
    Re-score dropped: outstanding 77  locked 2  backstop-skip 17

6946 s of background CPU is roughly **46 % of the day's whole background bill** (MetricKit:
`bg=252m`). But decomposing it changes what to do about it entirely:

| | cost |
|---|---|
| **ONE full pass** | **4214 s — 82 % of all full-pass time** |
| next two full passes | 449 s + 306 s |
| remaining seven full passes | 148 s *total* |
| all 56 light passes | 455 s (~7 % of the bill, median 8.4 s each) |

This is not death by a thousand cuts. It is one outlier, and the 56 light passes everyone would
reach for first are a rounding error beside it.

## The outlier's cause

That pass logged **`trigger=forced where=foreground`**. It began while the app was open, the app went
to the background, and it kept going — I/O-throttled — for **seventy minutes**.

`RescoreBackgroundPolicy` could not prevent it. Its first line is `guard isBackground else { return
.run }`: a foreground start is waved through once and **never re-examined**. Nothing inside the pass
looked at the app state again except to *label* the log line — the `where=foreground` in that very
log entry was written by code that had no intention of acting on it.

## The fix

The pass re-checks the app state **per night** and abandons if the app has gone away. Per night
rather than once, because the transition happens mid-pass by definition.

**Abandoning is safe, and this is the half that deserved scrutiny.** The watermark is written only at
the end of a completed pass, so an abandoned pass writes *nothing*: it returns before both the
watermark and the debt settle, leaving state exactly as an interrupted pass already leaves it — debt
still marked, and the next trigger re-runs it under a policy that *can* defer properly. The nights it
did finish are already persisted, so no work is lost.

A test asserts that ordering specifically, because getting it wrong is worse than the bug: writing
the watermark after stopping at night 3 would mark eighteen unscored nights as done, and no later
trigger would revisit them. That is silent data loss, not a saving.

The **light pass is exempt** — today-only, 8.4 s median, and it is what keeps the numerators moving in
the background. Aborting it would trade a real feature for almost none of the bill. The abort also
never fires at night 0: a pass that scores nothing is pure waste.

Reading the app state from inside the pass needed a nonisolated mirror.
`UIApplication.applicationState` is main-actor-isolated, and the scan runs in a `Task.detached` —
hopping to the main actor 21 times inside a background scan would serialise against the UI and
defeat the point. The mirror is `NSLock`-guarded (the primitive this file already uses) and is
updated by the **scene-phase hook itself**, not only by main-actor reads: the case it exists for is
precisely "the app went away and nothing else asked".

## Deliberately not changed

- **The light-pass cadence.** ~10 min median between triggers, 7 % of the bill. Slowing it would cost
  the background numerator updates for almost no saving.
- **The post-offload `newData` gate.** It is correctly scoped to the post-offload caller only,
  because an import or an edit changes scores *without* changing the HR fingerprint. The 4
  `forced newData=no` passes came from foreground opens and are cheap.
- **The 77 "already outstanding" drops.** These are the deferral system working — a trigger arriving
  while a pass is running is *supposed* to be dropped. They cost nothing; the log line counts them so
  the churn is visible, not because each is a fault.

## What the next install must show

1. **`gave up ×N (backgrounded mid-pass)`** on the `Re-score today:` line, on any day you open the
   app and then put it away while a full pass is running. A non-zero count here is the fix working.
2. **`longest` well under 4214 s** — that figure should now be bounded by how long a pass runs while
   the app is actually in front of you.
3. **`cpu bg=` substantially lower.** If the day's shape repeats, most of the 6946 s should be gone.
4. **Nothing unscored.** Day quality and the scores should still be complete: an abandoned pass is
   re-run, not skipped. If a day goes permanently unscored, the watermark guard has failed and that
   is the thing to report.
