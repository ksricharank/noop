# Fork release 11.1.0.16.3 (build 315)

Supersedes 16.2, which was cut and installed but shipped the day-quality score **inert**. Two fixes
and one addition, all on `feature/v15-widgets`; FEATURES set unchanged, so the counter stays at 16.

## 16.2 shipped no scores at all

Reported: "I thought we were backfilling the day quality? I don't see any scores there, and not the
LLM section either."

The nightly pass required `widgetAnchor(...)?.day == todayKey` — a condition borrowed from the
morning brief's "has tonight's night landed" test. It is wrong here, and it disabled the feature
outright: the anchor deliberately **carries yesterday's scored row** until today has a recovery of
its own, so the condition is false for most of the day, including the first pass after midnight —
the one that would have backfilled. Nothing was ever written to the series.

The brief needs that test because it speaks about TODAY and must not restate a stale carry. This
pass scores **finished days only**, so a fresh night was never a precondition: every day it grades
is already complete. The latch alone now decides, which is all "compute once per day" ever required.

The missing "What it means" section was the same cause, not a second bug — it only renders when
there is a score.

**A note on how this got through.** 16.2's tests all passed, and none of them exercised the gate:
they covered `daysToScore`, the input assembly and the latch as units, while the condition that
disabled everything sat in the engine between them. Compile-and-unit-test success said nothing about
whether the feature ran at all.

## Scoring is now incremental, not a nightly re-score

Maintainer: "I don't want the backfill to run every day. it should just be a one time thing… and
then a new score is computed each day?" Exactly that, and 16.2 did not do it.

The pass now reads which days the series already holds and scores only what is missing:

- **First run** — nothing stored, so every finished day is scored. The one-time backfill.
- **Steady state** — one new day per day.
- **A gap** that later gains data is filled without touching its neighbours.
- **A config change** re-scores history, driven by the latch's config fingerprint. This is the only
  case that justifies it: a finished day's inputs are fixed, so only the weighting can move its score.

16.2 re-derived every finished day on each run. The once-per-day latch kept that off the hot path,
but it still walked months of targets nightly to recompute values that cannot change.

## Ask the Coach, on the day-quality card

Mirrors the Today synthesis's affordance, as requested. Worth having specifically because the coach
now receives the day-quality **history** (the recent run plus both 7-day averages and the change), so
a question asked from the card lands in a conversation that can already see the trend it shows.

## What the next install must show

The score is the thing to check, since 16.2 proved that passing tests do not mean the feature runs:

- **Scores appear in Trends** — after the first sync on this build, the card should show a score and
  the chart should have history behind it, not a single point.
- **The strap log's `day-quality:` line** names how many days each pass scored. The FIRST pass should
  report many (the backfill); every later pass that day should report nothing, and tomorrow's should
  report one. If a later pass reports many again, the incremental path is not working.
- **"What it means"** should produce a narrative once a score exists and a provider is configured.

Still unverified on hardware from earlier builds: the water reminder's stale-request retirement (one
reminder per slot, no frozen figure), Configure coach's key/provider flow, the notification "Add a
cup" action, water on the widget faces, both buzz fixes, and the macOS idle-at-launch change.
