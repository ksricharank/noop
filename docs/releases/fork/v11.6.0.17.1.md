# 11.6.0.17.1 (build 373)

The first build past the uplift. Three repairs, all found by the 260914 log or the maintainer
using 17.0 on the phone.

## "Ask the Coach" opened Trends

Upstream's K3 promoted Coach to a top-level tab and switched to it by **literal** (`selectedTab = 3`).
This fork's order is Today/Day/Sleep/Trends/More, so tag 3 is **Trends**. Every tap on "Ask the
Coach" opened the Trends tab — a screen that loads perfectly and is simply the wrong one.

That literal is the exact trap [`PhoneTabOrder`](Strand/App/PhoneTabOrder.swift) was created to
remove after the 260908 reorder. It survived because **the tab shell read its own labels and icons
as literals** while taking only its indices from the enum: `PhoneTabOrderTests` stayed green while
the bar said something else. The shell now takes label, icon and index from `PhoneTab`, so there is
one source of truth, and the tests pin that no tab is the Coach.

Coach now switches to More and pushes `MoreDestination.coach`, so the tap lands in the chat and the
system Back button returns the way it came.

## "Day" is now "Recap"

The tab shows the retrospective read on a finished day ("How a finished day actually went"), which
"Day" did not convey sitting next to "Today", and `medal` implied an award rather than a summary.
Now **Recap** with `calendar.badge.checkmark`.

Deliberately not "Yesterday": the tab is a browsable date navigator, so a literal yesterday would be
wrong on every other day the user scrolls to.

## The re-score clock was measuring the wrong thing

The 260914 log appeared to show a runaway pass and a catastrophic read cost:

    re-score: gave up after 1802 s of a full pass
    analyzeRecent cost prep=600775ms (read=598352ms compute=2422ms)
    analyzeRecent store sql reads=608508ms/107

All three are artifacts. Every timer on the re-score path read `Date()`, which keeps running while
iOS suspends the app. The same log shows what actually happened two lines earlier:

    re-score: ABANDONED after 1/21 night(s)

**The abort gate fired correctly, after one night.** The pass was then suspended for half an hour
between two iterations of the loop, and the wall clock counted all of it. The 598-second "read" is
ten minutes of SQL that never ran — and it was about to be used as evidence for narrowing the
54-hour read window, which is the opposite of what the data supports.

Every timer on the path (pass, per-day prep, per-read, score) and the store's own `perfSqlRead/Write`
counters now use monotonic `DispatchTime`, which does not advance while the device sleeps. A
diagnostic may only assert what it can attribute; these were asserting suspension as work.

The gate itself was never broken and is unchanged.

## What the 260914 log says about the uplift

Verified independently of the fixes above:

- **HRV is recovering.** `avgHrv=nil` on all 18 nights from 08-25 to 09-11, then `36.4` on 09-12,
  `38.9` on 09-13, `34.0` on 09-14. The cutover is sharp and matches the WHOOP 5 R-R relabelling:
  new beats arrive labelled and score; legacy rows stay unscorable, as upstream documented. Three
  valid nights against `minNightsSeed = 4`, so Charge should return on the fourth.
- **Widget budget is healthy.** `spent=56/200 coalesced=10`, dedup suppressing ~52% of publishes.
- **Reads dominate the re-score, compute is free.** Excluding the suspended-app artifacts, reads are
  ~89% of pass time and compute totals ~1.4 s across 47 passes. The read window remains the right
  target — but the case for it now rests on numbers that mean what they say.
- **Day quality scored 7 days, not the forties.** Days are dropped with
  `configDropped(sleepNeedHours+sleepConsistency+habitualMidsleep)` — missing config inputs, not a
  fingerprint change. Still open; the log names the reason but not the per-day values.

## Known, not fixed here

- **Strap alarm: 14 of 14 `RUN_ALARM` commands return `FAILURE(0)`**, with the strap replying
  "invalid alarm id" and the alarm disabled anyway. This is **upstream's code and upstream's known
  gap** — the comment beside it already documents the same PENDING/FAILURE divergence from their own
  1119 log. Left alone rather than changing BLE behaviour on one log.
- **BLE wake rate: ~190k wakes/day, ~86% while locked.** Far larger in count than the 187 light
  passes/day this thread has been optimising. The log does not attribute energy per wake, so this is
  a lead, not a finding.
- **`workout detect kept=0` on every day** despite `runs=44 bridged=40`. Possible uplift regression.
- **Folder backup access is dead**: `scoped-access FAILED, bookmark FAILED`, no backup mode chosen.

## Verification

macOS `Strand` and iOS `NOOPiOS` both build. **2,128 / 2,130** app-target tests pass; the two
failures are `SkinTempAbsoluteDisplayTests` and `SleepCarriedStampTests`, upstream's own
date-sensitive tests, which fail identically on a clean `v11.6.0` checkout with no fork code present.
