# 11.8.0.18.16 (build 417)

The Charge flip, found. It was not the display, and it was not the light pass.

## What was reported

> It shows 36 on the charge when I first load the app, then goes to 66 or 67, then flips back to 36

and, a day later, the detail that settled it:

> the widgets now show the steps target etc against a charge score of 36, while the app itself is
> showing a steps target scored against a charge score of 67

Two processes, two different Charges, at the same instant. That rules out a rendering bug outright
— the widget extension does not run the display code. Both values physically existed.

## The cause

The 260906 abort gate breaks the day loop the moment the app backgrounds:

```swift
if !lightPass, offset > 0, RescoreBackgroundScheduler.isBackgroundedSnapshot {
    abandonedAtOffset = offset
    break
}
```

On a strap-only install the nights this pass scores **are** the HRV/RHR baseline — `hist` reads the
imported device id, which is empty. So a pass that stops at night 4 folds a 4-night baseline, and
pass 2 z-scores the night against a window it never scored. Being a full pass, it writes that value
over what a completed pass computed.

The abandonment `return` sits roughly a thousand lines **after** the persist. It skips the watermark
and the debt settle — nothing else.

Measured against the shipped scorer, same night, same inputs, only the folded window differing:

| Nights folded | Charge |
|---|---|
| 4 | **64** |
| 10 | 41 |
| 21 | **30** |

Below the seed gate (3 nights or fewer) the scorer returns nil rather than a wrong number — which
is the *other* screenshot, the one reading 36 under a "Last night" pill: a carried prior day, shown
because today's had been cleared.

## This is the 260903 bug arriving by a second route

The light pass was fixed in 18.x with `let recovery = lightPass ? nil : ...`, against exactly this
reasoning — the comment in the engine still describes "the same night scored Charge 22 on the full
21-night window and 47 on the light pass's". 22 ↔ 47 then; 64 ↔ 30 now.

That guard keyed on **which kind of pass this is**. The real invariant is **whether the baseline is
complete**, and three days later the abort gate created a second way to fold a short window that
`lightPass` cannot see. The guard is now `lightPass || wasAbandoned`, named `partialBaseline`, so a
third truncation route does not need a third flag. `wasAbandoned` is hoisted above the fold; it was
previously derived after the write.

## Why it started now

Upstream's #2296, taken in the v18 uplift, **deleted the measured-duration deferral**: a slow pass
is no longer held back, it runs and rests. The fork's abort gate then meets it at the next day
boundary. Abandonment went from rare to routine — **25 in a single log**, each writing a fresh wrong
answer from a different truncation offset.

Neither side is wrong alone. Upstream has no abort gate, so pacing is safe for them; the gate was
safe under deferral. The interaction is ours to own, and it is why the flip tracks the uplift rather
than the Sep 6 commit that introduced the gate.

The 06:30 reading has the same root: on a cold launch straight into the background — the overnight
BGTask wake — the pass runs, abandons, and leaves a truncated Charge sitting there until the morning
foreground pass corrects it. Not a default value. Last night's abandoned pass.

## Three ledgers, because none of this was answerable after the fact

The store keeps only the final value, so a flip leaves no trace. All always-on, counts-only:

- **`chargeWrite`** — every recovery write: value, `hrvNValid`, pass kind (`full` / `light` /
  `abandoned`), trigger. `nValid` is the tell: far below 21 on a `kind=full` line means a pass judged
  a night against a window it never scored.
- **`chargePublish`** — the widget snapshot's Charge, its anchor day (flagged `(carried)` when it is
  not today), and whether WidgetKit was actually asked to reload or the request was **withheld by the
  background budget**. A withheld reload leaves a correct snapshot behind a stale face, which from
  outside is indistinguishable from a wrong value.
- **`chargeShown`** — what the screen displayed and via which branch, on transitions only. A carried
  36 and a mis-scored 36 previously read identically in an export.

## Verification

Both app targets compile. `AbandonedPassBaselineTests` (6) pins the premise against the shipped
scorer — a 4-night fold must read >20 points above a 21-night fold for the same night — that a
sub-seed fold refuses rather than guesses, and the four guard outcomes. Mutation-checked: reverting
the guard fails two of them.

Full 2485-test macOS suite runs with only the **4 failures already present on a clean worktree**,
confirmed by stashing the change and re-running the baseline rather than assuming.

Worth stating plainly: every pre-existing recovery test supplies a fully-populated baseline and
asserts pure-function output. None constructs a truncated one, and none exercises the abandon/resume
cycle — which is how an error of ~30 Charge points shipped under a green suite.

## What the next build must check

- **Charge does not flip.** Same value at 06:30, at the morning open, and after a background sync.
- **Widget and app agree.** If they diverge, `chargePublish` now says whether the snapshot was stale
  (`reloadRequested=false`) or the value itself was wrong.
- **`chargeWrite` shows no `kind=abandoned` line carrying a value** — they must read
  `wrote=nil(preserved)`.
- **`hrvNValid` on `kind=full` lines reads ~21.** Anything far below is a truncation the guard did
  not catch, and the diagnosis is incomplete.
- If Charge still flips with all three ledgers clean, the mechanism is something else and the logs
  say where to look next.

## Not in this build

The tab-switch reload is diagnosed but untouched. It is **not** a re-score — no `analyzeRecent` fires
from any tab root. `LiquidTodayView.load()` re-runs ~20 store reads on every return to Today,
including a 200k-row raw-HR query and a full-history `StressModel`, because the `#849/#932` caching
fix (`todayHistoryWideLoadedSeq` / `todayHistoryWideCache`) exists in the classic `TodayView` and was
never ported to the liquid rewrite that replaced it as the default. **That gap is upstream's** — zero
references in their copy of the file too.

`TrendsView.multiMetricSeries` rebuilding seven full-history dictionaries per body evaluation is
ours, from 18.14, and the 1 Hz heart-rate sink triggers it continuously while the strap is connected.

Both are held for the refactor pass rather than folded into a fix build.
