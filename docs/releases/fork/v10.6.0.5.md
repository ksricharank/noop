## Reinstalling this build

**Clear the provisioning profiles first, then build.**

```bash
rm -f ~/Library/Developer/Xcode/UserData/Provisioning\ Profiles/*.mobileprovision
```

A free personal team issues 7-day profiles, and Xcode reuses an existing valid one rather than
minting a new one — so rebuilding does *not* reliably reset the clock. Verify the reset took by
reading the profiles' `CreationDate` (see FORK-RELEASE step 4). The app stops launching at expiry
regardless of anything in the code.

## New: Apple Health writes off, reads intact (`feature/health-read-only-sync`)

**The measurement.** The 260827 log's header line: `wakes=764 synced=31 coalesced=41 empty=608
avgSyncMs=10981`. 80% of the wakes were empty, and they are a **self-wake loop**: the HealthKit
observers register with `predicate: nil`, so NOOP's own writes wake them; the anchored delta query
then filters NOOP-authored samples out (`notNoopAuthored`, #375) and finds nothing — a process
resume spent learning we woke ourselves. Every real sync also runs all four writers, of which the
heart-rate writer re-deletes and re-saves a rolling 48 h window (~2,880 samples) whether or not
anything changed. The writes are the expensive half; the reads (daemon-side day-bucket aggregates)
are the cheap half and are what the scores consume.

**Why writes were on at all.** The launch-time resume (`refreshAuthIfPreviouslyGranted`) inferred
"user granted Health access" from *write*/share status alone — HealthKit never reveals read status.
So all-reads-no-writes resumed nothing: `auth` stayed `.unknown`, `enableLiveDelivery()` never ran,
and background ingestion was silently dead. The user enabled write-to-HRV **only to satisfy that
proxy**, which is what armed the self-wake loop. A bug, not a misconfiguration.

**The fix, two parts:**

1. **Resume from the stored read-type signature too.** `persistReadTypeSignature()` already runs
   only after a successful `requestAuthorization()` — a durable, write-independent proof the user
   completed the Health sheet. Either signal (any write grant, or the signature) now resumes and
   arms live delivery. The new-share-types re-request stays on the write-granted path only.
2. **A "Write strap data to Health" switch** on the Apple Health screen, default **ON** (existing
   installs byte-identical until flipped). One guard in `writeBack()` — the single funnel both
   write paths use — plus an early bail in the background write task. Reads untouched.

Decisions are pure in `Strand/Data/HealthSyncPolicy.swift` (shared, so the macOS-hosted suite can
test what the iOS-only bridge can't link), pinned by 7 tests including the default-ON trap and all
four resume quadrants.

**To get the intended setup:** flip the new switch off, then (optionally) revoke the HRV write
grant in Health › Data Access & Devices — the resume no longer needs it.

**What the next log must show:** `wakes` collapsing from ~764/day toward the handful the watch's own
data produces; `empty` far below 80%; `avgSyncMs` well under 11 s with the writers gone. And the
read side must NOT regress — `apple-health` day counts and sleep/recovery coverage are the half this
feature exists to keep.

## Deprecated: `feature/backfill-skip-empty-recontinue`

The 260827 log is the measurement this branch shipped to produce, and the verdict is unambiguous:
**308 offload sessions, 142 caught-up sentinel lines, zero sentinel stops.** The guard never fired.

The mechanism is an off-by-one in which session the sentinel belongs to. The guard read the sentinel
of the session that *just ended* — but the sentinel only ever arrives in the session *produced by*
the re-kick (the empty one), which persists no rows and is already stopped by the existing #1144
guard. Every productive session ends on a live trim, so the flag was never set at the moment the
decision ran. The 10.6.0.4 notes' "0 of 58 productive sessions suppressed" analysis proved the guard
safe without checking it was *reachable*.

Fixing it needs cross-session state (remember "the last offload ended caught-up" across `begin()`),
a more invasive change the same log argues has modest value: Low Power Mode plus the existing
empty-offload backoff already brought empty sessions from 9.1/hr to 6.2/hr without it. Dropped from
`FEATURES`; the branch stays in the repo as the record of the negative result.

## Also measured in the 260827 log, not addressed here

- **Re-score CPU is now the dominant phone-side cost and it is growing**: 42 runs totalling
  18.6 min, worst 216 s, worst prep 148 s — against 0.5–4 s medians for identical work. The
  contention theory is now *weakened*: slow preps had **fewer** offload writes within 90 s than fast
  ones (1.1 vs 1.7 average), so the cause is genuinely unknown. Next step is instrumentation (split
  prep into DB-read vs compute; split `syncRead` into actor-wait vs SQL), not a fix.
- **Upstream's #1642 CLIENT_HELLO fix works** — 6 writes in 22.9 h, down from constant 5 s churn.
- `lastSeen=19h 33m` on an actively-syncing strap is a stale registry display field.
- 22 `Disable Alarm` sends for an alarm that is disabled.
- Backups still silently broken (`scoped-access FAILED, bookmark FAILED`, no mode chosen).
