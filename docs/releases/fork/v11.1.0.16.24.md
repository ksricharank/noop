# 11.1.0.16.24 (build 336)

The day-quality histogram showed stale values for past days across three builds. The 09-09 log
finally carries the diagnostic that names the cause, so this build fixes the actual bug rather than
another guess at it.

Maintainer, correctly: *"the current score seems to be accurately reflected. So maybe it is just a
backfill issue."*

## What the diagnostic said

    day-quality: scored 4 day(s), newest 2026-08-18=37
    day-quality: already scored for 2026-09-09 under this config   (x12)

**Four days, newest three weeks old, then latched.** That single line is what three builds of guessing
could not establish.

The cause is in the WRITER, one layer below where the previous two repairs looked. `existing` holds
the days the series already contains, and `daysToScore` subtracts them — so the pass scored the four
days that were **missing** and skipped the ~43 that were **present but stale**. `rescoreAll` would
have cleared `existing`, but it is driven by `configChanged`, which was false because an earlier pass
had already latched that fingerprint.

The same latch problem as before, in a different place. The `force: true` path clears `existing` and
bypasses the latch, which is what actually rewrites those 43 days.

## The detector is now a direct comparison

Re-score the recent days; check whether the stored numbers match. No threshold, no inference about
provenance.

Both earlier attempts asked indirect questions and both were silent on the real data:

| attempt | what it asked | why it failed |
|---|---|---|
| 16.22 | `configChanged` | records that a pass RAN, not that values are current |
| 16.23 | shape: "nothing ≤ 0 across 20+ days" | real window is **14** days (under the gate) and holds a negative day (defeats the other tell) |

The second is the more instructive failure. It was tested against a **25-day synthetic fixture** and
passed. The fixture was written to match the theory instead of the screenshot that had already been
provided — so it was green on invented data and silent on the data it existed for.

The comparison cannot be defeated that way: it asks the actual question. The view already re-scores
its window for the Insights cards, so it costs nothing; it samples 5 recent days, because one
disagreement is enough to trigger the full forced re-derivation.

Tests now use the **reported** window sizes rather than convenient ones. The 14-day case with a
negative day is the first test in the file and fails the retired heuristic by construction. Also
pinned: rounding tolerated but real drift caught; a day absent from either side ignored (a missing
day is the incremental path's job, not a reason to force a full pass); the check stays bounded.

## Window selector moved

It sat at the section's top with full card spacing on both sides, which placed it visually between
the Insights card above and the chart below — belonging to neither, and implying a scope over the
whole section that it never had. It only ever drove the chart and its footer.

Now grouped with the chart at tight spacing. It cannot go inside `ChartCard`, which height-constrains
its `chart` closure and would squeeze the plot; adding a slot to a shared design component for one
caller is the wrong trade.

## Standing items, unchanged

- The **54-hour light-pass read window** remains the largest known battery cost (~59 % of every light
  pass's ~5 s of SQL, 187 passes/day). On the scoring path, so it needs a byte-identical-score oracle
  first.
- **Effort inflated by a noisy R-R night** (09-09: `rejected` 2 %→17 %, `dupBeats` 143→821, same
  `meanNN`). Effort accepts beats the HRV path already flags as unreliable. Deferred by the maintainer
  until it repeats.
- **BLE wake volume is payload, not overhead** — ~1.5–1.8 rows per notification, so the count tracks
  rows transferred. An earlier note calling the overnight offloads a large battery item was wrong: it
  read a payload counter as an overhead counter.
