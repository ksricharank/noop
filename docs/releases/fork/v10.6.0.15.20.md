# Fork release 10.6.0.15.20 (build 310)

One fix on `feature/v15-widgets`: the wrist buzz now defaults ON. No change to the FEATURES set,
so the fork counter stays at 15.

## "My whoop is still not buzzing for water"

Reported from the device on 15.19. The wiring was correct end to end — the post sites call
`buzzForNudgeIfEnabled`, the cue keys default on, the link check is right. The master toggle simply
**defaulted off**, so the buzz that was added on request arrived silent and read as broken.

That default was the wrong call. A cue nobody asked for should default off; this one was asked for.
Every cue now defaults on and the user switches OFF what they do not want, rather than hunting for
why a feature they requested makes no sound.

It is safe to default on because it is self-limiting rather than merely quiet:

- each underlying nudge keeps its **own** enable toggle, so this can never buzz for a nudge that is
  itself off;
- the buzz still requires an **encrypted, bonded** link, so a charging or out-of-range strap gets no
  cue rather than the app pretending one landed.

The same change exposed a latent mismatch: `AutomationsView`'s `@AppStorage` default was `false`
while the logic default is now `true`, which would have rendered the switch OFF while the buzz was
in fact firing. Both defaults are now stated together with a note that they must agree.

## What was NOT changed, and why

**The Inactivity ("move") reminder.** This is the only thing in NOOP that a "steps buzz" could come
from — there is no steps-goal notification in the app at all, on either platform. It is a separate
upstream feature with its own switch, quiet hours and threshold, and it is **also off by default**.

Turning on an upstream feature the maintainer has not asked about is not a release note's call to
make silently, so it stays off. To feel it: **Automations → Inactivity reminder**, which is
independent of the "Buzz my wrist" master.
