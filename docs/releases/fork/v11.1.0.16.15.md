# 11.1.0.16.15 (build 327)

Three reports from the 16.14 screenshots: an explanation that no longer matched its own arithmetic, a
trend comparison that lied about its window, and day quality living in two places at once.

## The step explainer describes the curve the code runs

The screenshot said it plainly:

    STEP TARGET → 9200
    Charge 60 is mid-range (34–66) → base 8000 steps

The continuous curve shipped in 16.14 but the explainer still described the three bands it replaced,
so the stated arithmetic could not reach the answer printed above it. An explanation that does not
arrive at its own number is worse than none.

The block now names the base the CODE derived, describes the scale as its two endpoints and the
slide between them, and closes on the target — the same shape the Calorie block uses:

    STEP TARGET → 9200
    Charge 60 → 9200 steps
       (the scale runs Charge 33 → 6000 up to Charge 67 → 10000, sliding with every point in between)
    body check: HRV 30 ≈ your usual 31, resting HR 66 above your usual 64 → all normal → no reduction
    target = 9200 (rounded to the nearest 50 so the number doesn't pretend to be exact)

Two smaller defects surfaced while rewriting it. The body-check line ended in **two** verdicts ("→
all normal, nothing taken off") because `bodyCheck` already supplies one. And the bounds line was
compared against the UNROUNDED sum, so "kept inside 4000–12000" fired on ordinary days that were
never clamped — it now prints only when a bound actually moved the number. "never set below 4000 or
above 12000 → 9200" invited the reader to hunt for where 9200 came from and find nothing.

A test walks charge 0–100 and asserts the named base equals the derived one at every point — the
property that had silently broken.

## The trend comparison was mislabelled, not miscalculated

Reported as "the day quality trend always seems to do compare vs next 7 and prev 7 — is that a bug?"

The arithmetic was RIGHT. With the 13 days on screen, the last seven averaged 62 and the six before
them 69, so −7 was correct. The FRAMING was wrong, twice:

1. The "prev 7" bucket held **six** days while the label claimed seven. A 7-day mean compared against
   a 6-day mean is not like-for-like.
2. Both halves were hard-coded at 7 regardless of the selected window, so 14d, 30d and 90d all
   produced the identical figure — **the window selector did nothing to that footer.**

Each half is now half the window (14d compares 7 vs 7, 30d compares 15 vs 15, capped at 30 so a
90-day view compares months rather than half-quarters). The label states the real bucket size. And
the delta is **withheld entirely** unless both halves are full — with 13 days the footer now shows
mean / best / days rather than a comparison it cannot honestly make.

## Day quality leaves Trends; Sleep gains the same block

Day quality is now only on the Day tab — card, trend, calendar strip and its settings card. Trends
keeps no second copy, which is also the safer arrangement: two surfaces rendering one score is the
divergence the parity rule warns about, and Trends is the poorer home since it cannot browse days.

Sleep gains a "Rest trend" section. It previously had one fixed 30-day duration chart with no way to
widen it, while Trends carried windowed views for every other metric. The new section reads the same
stored `sleep_performance` series the Rest hero shows, so the two cannot disagree about a night.

`ScoreTrendSection` is written ONCE and used by both tabs — window selector, chart, honest footer,
and the calendar heat strip ported from the Trends year strip (which answers "how consistent has this
been", a question a line chart cannot). Writing it twice is what produced the comparison defect above.

The new `SleepSection` case is Apple-only. Safe to diverge: `sleep.sectionOrder` is not in the
`.noopbak` whitelist — Android's own `SleepLayoutPrefs` says exactly that and already carries two
platform-only sections for the same reason. A stale comment in the Swift test claimed the keys had to
match Android byte-for-byte; it is corrected.
