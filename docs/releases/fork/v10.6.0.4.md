## Reinstalling this build

**Clear the provisioning profiles first, then build.**

```bash
rm -f ~/Library/Developer/Xcode/UserData/Provisioning\ Profiles/*.mobileprovision
```

A free personal team issues 7-day profiles, and Xcode reuses an existing valid one rather than
minting a new one — so rebuilding does *not* reliably reset the clock, and the app can die mid-week
after what looked like a fresh build. This build's profile expires **1 September 2026**; the app
stops launching then regardless of anything in the code.

If the app has already died, this is still the fix — it just costs a reinstall.

## Strap battery

**A sync no longer asks the strap for history it has just said it does not have.** In a 5.5-hour log
the app ran **107 historical-offload sessions, 48 of which (45%) returned zero rows**. Every one of
those had the same shape: a productive session, an immediate auto-continue, and a second session
that ended on `trim=0xFFFFFFFF` — the strap's own "nothing past the last trim" sentinel. That second
round trip cannot return data. The strap has already answered the question the re-kick asks.

The cause is specific to the 5.0/MG. The auto-continue's primary test — "does the strap report data
newer than ours?" — reads `GET_DATA_RANGE`, which is deliberately wired `feedsSync: false` on a
5/MG pending hardware confirmation of its field offsets. So that value is always absent (the log
prints `strap-reported newest ?` on every line), the primary test can never fire, and every
productive session falls through to a fallback rule that re-kicks unconditionally and learns
"caught up" only by paying for the empty session. A WHOOP 4.0 was never affected: it feeds the
range, so the primary test answers first.

The decision now stops when the session it is continuing from ended on that sentinel, and **says so
in the log** rather than going quiet — a silent stop is indistinguishable from a frozen cursor or a
spent retry budget when reading an export later.

**A real backlog is unaffected.** The strap reports a live trim while it still holds records and
only reaches for the sentinel once it does not, so a deep overnight drain still runs back-to-back
passes. The periodic floor keeps draining across connects either way.

**Expect roughly half the offload sessions** — 107 → ~59 on a comparable day. That is the number
this build exists to be measured against.

## What this build deliberately does *not* fix

The same log shows re-score passes taking **101 s and 73 s**, against 0.7–3.7 s for the same eleven
nights elsewhere in the same session — with the day cache reusing 10 of 11 days in both cases. The
same one day of work costs 489 ms or 45 s depending only on what else is running. That is a
separate defect on the storage/concurrency path, not radio waste, and it is **not addressed here**.

It is left out on purpose. Both changes suppress work, so shipping them together would make neither
measurable; and the contention theory for the spikes — which
`feature/locked-rescore-deferral` already asserts from its own overnight log — is still unproven.
Removing 48 pointless offload sessions is what makes the next measurement readable: a 45 s prep that
survives this build is evidence contention is not the whole story.

Note also that the existing re-score deferral is scoped to the sleep window (22:00–07:00 by
default), so it does not cover a daytime log like this one. That is by design, not a regression.

The four new pins are: the sentinel stops a continue the fallback rule would have made; a
no-sentinel control still continues (proving the new guard is what stopped it, not something else);
the sentinel outranks a wide reported backlog gap; and the new parameter defaults off, so every
pre-existing caller and fixture is byte-identical.

Both app targets were compiled locally because **no default CI covers app-target Swift** —
`app-build.yml` is disabled and `swift-packages.yml` only tests `Packages/**`. Values above are the
effective build settings (`-showBuildSettings`), not the files they are assumed to come from.

**The build number is 248, not 247.** Upstream bumped its own staging build number mid-rebuild, which
collides with the fork's on `project.yml` every time — the fork counter and upstream's counter are the
same global key. Resolved by taking the higher value: a build number may only ever increase, and iOS
refuses an app/widget mismatch (#416), so both sides take 248. Expect this conflict on most rebuilds;
it is a two-line resolution and not a sign that anything is wrong.

**Not verified: anything on hardware.** This build has not been run against a strap, and the change
is on the CoreBluetooth offload path, where compiling proves nothing about connection behaviour. The
predicted 107 → ~59 session count is a prediction, not a result. It needs a full day's wear and a
fresh strap log compared against the 260825 one on three numbers: total offload sessions (107),
zero-row sessions (48), and worst re-score (101 s — expected to persist, per the section above).

Everything carried from 10.6.0.3 remains unverified on hardware too: the coach timeout budget, the
Live Activity race, the locked-cadence pause and the sleep-window pause.

## Upstreaming

This one is worth sending upstream: the waste is not fork-specific, it affects every 5.0/MG owner,
and the fix is a guard plus a log line. Two things to carry with it — the **Android twin** in
`com.noop.ble`, which this branch deliberately omits (personal fork, iOS device only), and the note
that the underlying cause is `GET_DATA_RANGE` being held at `feedsSync: false` for the 5/MG. If a
real strap ever confirms those offsets, flipping that flag makes the primary test work and is the
better fix; this guard remains correct either way.
