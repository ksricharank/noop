# Fork release 11.1.0.16.2 (build 314)

Three things: the day-quality score (a new long-run motivation surface in Trends), the real cause of
the duplicate water reminders, and all coach configuration consolidated into Settings. FEATURES set
unchanged, so the fork counter stays at 16.

## The water reminder: the actual bug, after two wrong diagnoses

Reported as a stale "5 of 21 cups" arriving repeatedly, each followed ~30 seconds later by the
correct figure. The decisive detail was the maintainer's: the SAME number, many days running.

**Cause: pre-260903 repeating notification requests, never cancelled.** The old reminder scheduled
`UNCalendarNotificationTrigger`s with `repeats: true`, each carrying a SNAPSHOT of the cup count at
schedule time. The 260903 rewrite to sync-driven posting added the new path but never removed the
old requests, and iOS fires a repeating request with its original body indefinitely. The phone was
running two reminder systems: the frozen one and the correct one. Now retired at launch on both
platforms, including delivered copies so the stale text clears from the shade.

Two other bugs were found and fixed on the way to it. Both are real; neither was what was reported,
and the notes are explicit about that:

- **Lost writes on fast taps.** `logHydration` is a read-modify-write and the +/- buttons call it
  from detached tasks, so concurrent taps each read the same running total and wrote back only their
  own increment. The on-screen count still looked right (the optimistic cache cannot miss a tap);
  only the stored series fell behind. Every hydration mutation is now serialised — removing the gate
  fails two of the three new tests, with six logs banking one value.
- **A mark-after-await race** between the reminder's two call sites, with an LLM title call in
  between. Real, kept, and its comment no longer claims it was the reported bug.

**And one non-bug, corrected.** A change claiming the old code fired reminders at midnight was
WRONG — the `dueSlot` guard already preceded the branch in question. A standalone reproduction of
the pre-change function returns false at 00:00, 02:10, 06:00 and 07:59. That change only deleted a
dead redundant branch; the comment and test doc now say so rather than asserting a defect that never
existed.

## Day quality score

One number per finished day (0–100), for the long-run motivation the daily synthesis cannot give —
the synthesis is about today; this is a closed book about yesterday, and a trend to keep pointing up.

**Two halves, 60/40 by default and configurable.** EXECUTION is what the wearer controlled (steps,
calories, effort, water); RECOVERY is what the body did with it (sleep vs need, HRV and resting HR
vs their own baselines). Blended into one number, a hard-charging week could hide a body falling
apart and a rest week would look like failure.

**Reaching 100 requires exceeding targets.** Components score above 1.0 when a target is beaten, up
to a configurable ceiling (default 125%) — so a big day is not punished for being hard. The BOUND is
what keeps it honest: a 5×-steps day with a skipped workout gains 3.75 points and still scores below
a day that did the work, and 400 000 steps scores the same as 40 000.

**A hard-day credit, configurable.** Targets shrink on a low-charge day, so hitting them is easier —
which means a score computed purely against the day's own targets can trend UP through a
deconditioning stretch. The execution half is scaled by how demanding the day's targets were against
the wearer's recent average, clamped to ±15% and halved at the default so a rest day still reads as
a rest day.

Three rules keep it truthful, each with a test: every component caps; a component with no data is
ABSENT rather than zero (its half's share passes to the other, and the card names what was missed);
and below three components there is NO score rather than a low one — a gap in the trend is honest, a
30 built from one measurement is a fiction.

Graded against the targets THAT day set, by calling the same `Repository.liveTargets` the Today strip
and widgets call. Not a stored copy: the number the score divides by is the number the wearer was
shown, and one formula change moves both.

**Computed once**, when the night's sleep is scored and the new targets are set — gated on the newest
scored day being today, plus a day-and-config-keyed latch. Moving a slider re-scores history
immediately rather than waiting for tomorrow. History is backfilled, so the trend has shape the first
time it is shown.

**In Trends:** the score card at the top (band, both halves, "How this was computed", "What it
means"), the trend chart below it (self-hiding under two points; footer leads with the signed 7-day
delta, because the direction is the point), and the three knobs at the bottom, collapsed.

The coach now also receives the score history — the recent run plus both 7-day averages and the
change — so it can comment on the trend and not only on today.

## Configure coach

604 lines of configuration — 57% of CoachView — sat above the chat, so "Ask the Coach" meant
scrolling past setup to reach the conversation. Provider, key, model, the three data consents and the
prompt editors are now in **Settings → Configure coach** (collapsed by default). CoachView is the Q&A
alone, 1056 → 414 lines, and Ask the Coach lands on the chat.

The code was MOVED, not rewritten — same bodies, same engine accessors, same keychain flow. Two
things changed shape: the four prompt editors now share one component instead of being three
hand-rolled copies of a ~70-line block (`ai.dayQualityPrompt` had no editor at all before and now
does), and the unconfigured branch is a pointer to Settings rather than a second copy of the setup
card.

## What only an install can verify

Everything user-facing here is unexercised on hardware:

- **The water reminder.** The fix removes requests that live in iOS's notification store, so the
  proof is a day with exactly one reminder per slot and no stale figure.
- **The day-quality card.** No score exists until a night is scored under this build. Watch the
  strap log's `day-quality:` line for the backfill's cost on a real history.
- **Configure coach.** A large UI relocation; the key/provider flow is only exercisable by hand, and
  compiling says nothing about how the setup card behaves inside a disclosure group. Worth clicking
  through first.
- Still carried unverified from earlier builds: the notification "Add a cup" action, water on the
  widget faces, both buzz fixes, and the macOS idle-at-launch change.

Before installing: clear the stale provisioning profiles —
