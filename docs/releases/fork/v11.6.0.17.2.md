# 11.6.0.17.2 (build 374)

17.1's three repairs, plus the one the BLE investigation turned up. Supersedes 17.1, which was
built but never installed.

## The BLE wake totals were counting every locked notification twice

The 260914 log's headline battery number — `189873 total` wakes yesterday, `9126/h` this session —
was wrong, and the investigation into it found the counter rather than a drain.

`recordNotify(_:locked:)` files a locked notification under **both** `"puffin"` and
`"puffin.locked"`. The suffixed key is a SUBSET view for attribution, not a channel of its own, but
both total lines summed the dictionary wholesale:

| reported | actual |
|---|---|
| 189873 total (yesterday) | **104407** |
| 110233 total (today) | **59138** |
| 23117 total (session) | **11747** |
| 9126/h | **4699/h** |

Every fixture in `BatteryDiagTests` predated the lock split and carried no `.locked` key, so the bug
was green in tests and wrong only in the field. That is the same shape as the 25-day synthetic
fixture that hid the day-quality staleness bug in 16.23: a test that passes because it does not use
the shape the recorder actually produces. The two new cases use the real shape.

## What the corrected number says: this is payload, not overhead

The remaining ~104k/day is not the phone being woken 104,000 times. Measured from the same log:

- **30,583 rows arrived across 11,727 puffin notifications = ~2.6 rows each**
- Backfills fire on a clean **10-minute cadence** — 19 bursts in 2.5 h (`12:02`, `12:12`, `12:22`, …)
- The rate limiter **declined 17 further offers** (`strap skipped (rate-limited; last 4s ago)`)
- Every R-R emission is `path=historical` — offload bursts, never live streaming

Notifications handled *inside* a burst are not independent process resumes. Ranking this above the
light-pass read window compared two different units; the read window remains the right target, since
reads are ~89% of pass time against ~1.4 s of compute across 47 passes.

## Also in this build (from 17.1)

**"Ask the Coach" opened Trends.** Upstream's K3 switched to Coach by literal (`selectedTab = 3`);
tag 3 is Trends in this fork's order. It survived because the tab shell read its labels and icons as
literals while taking only indices from the enum, so `PhoneTabOrderTests` stayed green while the bar
said something else. Label, icon and index now all come from `PhoneTab`.

**"Day" is now "Recap"**, with `calendar.badge.checkmark`. The tab is the retrospective read on a
finished day; "Day" did not convey that beside "Today", and a medal implies an award. Not
"Yesterday" — it is a browsable date navigator.

**The re-score timers measured wall time.** `gave up after 1802 s`, `prep=600775ms
(read=598352ms)` and `reads=608508ms/107` were all artifacts of `Date()` running through app
suspension; the same log shows the gate firing correctly after `ABANDONED after 1/21 night(s)`. Every
timer on the path, and the store's own SQL counters, now use monotonic `DispatchTime`. The gate
itself was never broken.

## The pattern worth noting

Three of this build's four fixes are **instrumentation that lied**, each making the app look worse
than it is: suspension reported as work, locked wakes counted twice, and a wake rate compared against
the wrong unit. A diagnostic may only assert what it can attribute — and a fixture that omits the
field under test cannot catch it failing.
