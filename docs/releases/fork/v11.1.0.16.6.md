## Choose which device counts your steps

Automations → Step count, above hydration, per the maintainer's placement. Strap (the default, and
every prior build's behaviour) or Apple Health.

The interesting part is WHERE the override lands, because that is what makes it consistent.
`Repository.days` merges the imported and computed sources only — Apple Health is NOT in it, which
is why both Today views reach for `appleDaily` separately as a fallback tier, and why every other
reader (the targets strip, the pacing proration, the day-quality score, the coach, the export) sees
the strap's count and nothing else. Overriding the field inside the merge means all of them keep
reading `row.steps` and get the chosen source, with no per-surface knowledge of the rule.

That matters because the alternative is already visible elsewhere in the app: CALORIES are resolved
Apple-first on the Today tile (#616) and strap-first in the merged row, so the tile and the targets
strip can legitimately show different numbers for the same day. Doing steps the same way would have
repeated that.

Modelled on the `mergeActivityFileSteps` fold directly above it, including its `steps > 0` rule — a
stored zero means "nothing recorded", not "you took no steps", so a day the Watch was charging
cannot overwrite a real count. A day the other device missed falls back rather than blanking.

**Steps only.** `activeKcalEst` is deliberately untouched: it is NOOP's own HR-derived estimate and
an input to strain, so swapping its source would silently re-base effort history. A test pins that
the steps toggle cannot reach it.

### It moves the numerator, not the target

Recorded because I got this wrong and the maintainer corrected it: "I thought the steps target was
independent of the apple stream. It was only the steps n value, not t."

Correct. `DailyTargets.stepsTarget` takes charge and readiness only, and neither `ReadinessEngine`
nor the recovery math reads steps, so no step count from any source can move the denominator. I had
asserted otherwise twice — once in conversation, and once, worse, in the code as the stated
rationale for the HealthKit observer below, where it would later have been read as the reason that
decision was made. Both are corrected, the card's own copy no longer repeats it to the wearer, and a
test pins the target's independence so the claim cannot return by assertion.

### Freshness, and an honest reason for it

The maintainer asked whether the count could update more often than the daily pass. It already did,
and by more than assumed: the light pass rides completed strap offloads (~10 min) and the merge
re-runs with it, so the preferred count moves on the same cadence as every other numerator.

The real gap was underneath. Apple's step ROWS are refreshed by `HealthKitBridge.sync` alone —
foreground, or an hourly observer wake for some other type — and `.stepCount` was not an observed
type, so in the background the data could be an hour stale however often the merge ran.

`liveQuantityIds` excluded steps because they "don't move a score". That was already only half-true
(day quality grades steps against their target; pacing compares them with the prorated pace), but it
held in PRACTICE because the numerator came from the strap and arrived with every offload. What the
toggle changes is that a source with different freshness can now feed those readers.

So a step-count observer is registered, GATED on the preference: a strap-preferring install pays no
extra background wakes, which is the whole point on the path this fork spends its time trimming.
Switching back retires the observer AND disables its background delivery — the registration loop
only touches types still in the list, so a dropped one would otherwise keep waking the app forever.
The bridge observes the preference change itself and re-arms, so a switch takes effect immediately
rather than at the next launch.

## Log a cup of water with a double-tap

"A tap on the device adding a cup of water without me having to do anything on the phone itself."

A new `logWater` action on the EXISTING double-tap picker, so no new gesture plumbing. It fires
LIVE: `dispatchLiveGestureIfFresh` accepts a gesture within 45 s of the strap's own clock and works
mid-offload, so the cup lands in real time rather than at the next sync.

It writes through `Repository.logHydration` — the same call the +Cup button and the notification
action make — so it inherits the 260904 serialisation and cannot disagree with the Today card about
the day's cups. It buzzes the `.water` cue on success, which is not decoration: a double-tap has no
on-screen feedback by definition, so without the buzz the wearer cannot tell a logged cup from an
unrecognised gesture. A WHOLE cup, not a half — the gesture is coarse and unprompted, so it should
mean the common case. A no-op when hydration tracking is off, and the log line says why.

Note the strap exposes a SINGLE double-tap gesture, so selecting this replaces whatever the action
was set to before.

## The release tooling's wrong-base trap, fixed

Written up as unfixed in the 16.5 notes; fixed here, having cost a detour on two consecutive cuts.

The v16 line is meant to build on the v11.1.0 TAG. Nothing enforced it: the script hardcoded
`$UPSTREAM_REMOTE/main`, which merely happened to equal the tag the day v16 was created.

  * **16.4** — local `upstream/main` was 38 commits past the tag, so the first assembly carried ~40
    upstream commits never present in the installed build. Caught only by diffing the assembly
    against the previous release branch and noticing the file count was far larger than the change
    justified.
  * **16.5** — pointing `UPSTREAM_REMOTE` at a bare pinned ref made `git remote get-url` fail, and
    the existing fallback silently chose `origin/main`, the fork's mirror, which has DIVERGED from
    the tag. Same wrong-base outcome by a different route.

Both share a shape: the base was decided by accident, and the script announced it only in a line
easy to skim. It is now an explicit `UPSTREAM_PINNED_REF`, overridable per-run with `UPSTREAM_REF`,
and a ref that does not resolve is FATAL rather than a silent fallback — building on the wrong base
is worse than not building. Verified: a bad ref exits non-zero having created no branch.

The standing advice from the 16.5 notes still applies as a backstop: diff a fresh assembly against
the previous release branch and check the file count is what the change justifies.
