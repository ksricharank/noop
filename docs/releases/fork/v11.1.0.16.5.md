# 11.1.0.16.5 (build 317)

The Trends range control now precedes the chart it drives, and coach-written prose renders its
Markdown. A small build on top of 16.4.

**16.4 (build 316) was cut but never installed**, so this install carries BOTH builds' changes: the
reminder delivery windows, the water reminder's move to Automations, the two notification-title
fixes, and the corrected buzz diagnostic all arrive here for the first time. Read the 16.4 notes
alongside these — its "what the next install must show" checklist still applies in full.

## The day-quality trend span

The maintainer asked for a week / two-week / month / six-month / year selector on the day-quality
trend, then found the answer themselves: "the window selector already exists further down in trends
- maybe just moving it up will fix it?"

That was right, and the situation was better than it looked: `dayQualityTrend` ALREADY windowed on
the shared `range` (W / M / 3M / 6M / 1Y / ALL, with the auto-widening that keeps a short empty
window from reading as "no data"). The only defect was placement. The selector rendered at stagger
index 4 while the day-quality chart sat at index 1, so the control that governs the chart appeared
BELOW it, and the span therefore read as fixed. Moved above it — no new state, no second control,
and every chart the selector applies to now follows it.

Left deliberately BELOW the day-quality card itself. That card is a single finished number for
yesterday, not a windowed series, so a range control above it would imply it responds to the span.
It does not, and implying otherwise would be a worse bug than the one being fixed.

Worth recording as a general lesson: the requested feature already existed and the report was really
about affordance. Building a second selector — the obvious reading of the request — would have
shipped two competing controls for one piece of state.

## Coach bold, two independent causes

Reported as "the coach response format doesn't show bold text correctly". Two unrelated faults, and
which one the maintainer saw depends on which surface they were looking at:

1. **Literal asterisks.** `DayQualityCard` rendered the narrative through a plain `Text(narrative)`,
   so the `**bold**` the model emits appeared as raw asterisks. The Today synthesis and the Q&A
   bubbles have used MarkdownUI since they shipped; this card was added later and did not, so it was
   the single surface showing syntax. Now Markdown with `.strandSynthesis`, which preserves the
   footnote scale and secondary tone the card already had — only the formatting changes, not the
   type size.
2. **Bold that was not bold.** The theme rendered `strong` as `.semibold`: roughly a 100-weight step
   against a 15pt regular body, and nearly invisible on the frosted Charge-tinted bubble. So even
   where Markdown WAS working, a correctly-emphasised reply looked like one with the bold stripped.
   Now `.bold`. Headings stay semibold — they are already separated by size and margin, and a
   full-bold heading inside a 560pt bubble is the shouting the theme's own doc warns against.

`CoachMarkdownRenderingTests` is new, written in the `NotificationActionWiringTests` idiom because
this is the same class of bug: a step present on one surface and absent on another, invisible to a
behavioural test because every part compiles and each piece works in isolation. It asserts that all
four coach-prose surfaces render through MarkdownUI with a theme applied, that the narrative has not
regressed to a plain `Text`, and that `.strong` is bold — the last scoped to the `.strong` block, so
the headings' legitimate `.semibold` cannot make it pass or fail for the wrong reason. Verified to
fail against both pre-fix states (5 failures, accurate messages).

## A tooling trap found while cutting 16.4 — still unfixed

Recorded here because it will re-fire on the next cut and cost the same detour.

`Tools/build-release-branch.sh` hardcodes its base as `$UPSTREAM_REMOTE/main`. Every v16 assembly is
supposed to be built on the PINNED `v11.1.0` tag — the FEATURES comments say why ("a released point
is a tested one") — but that pin only ever held because `upstream/main` happened to equal the tag
when v16 was created. Nothing enforces it.

By the 16.4 cut, local `upstream/main` was 38 commits past the tag, so the first assembly came out
with a 77-file diff against 315: ~40 upstream commits (Android tests, skin-temp work, docs) that
were never in the installed build. `--no-fetch` does not help, since the drift was already fetched.
Caught by diffing the assembly against the previous one and noticing the file count was far larger
than the change justified; rebuilt against the tag via a temporary `refs/remotes/pinned/main` ref,
after which the diff was exactly the expected files.

**Before the next cut**, give the script an explicit `UPSTREAM_REF` (defaulting to the pinned tag for
the v16 line) so the base is a stated decision rather than an accident of fetch timing. Until then,
ALWAYS diff a fresh assembly against the previous release branch and check the file count is what the
change justifies.
