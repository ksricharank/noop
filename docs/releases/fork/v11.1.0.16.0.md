# Fork release 11.1.0.16.0 (build 312)

The uplift to upstream **v11.1.0**. The fork's feature set is unchanged — the same five features,
rebased off a 10.6.x base onto the v11.1.0 tag. The counter moves to **16** and its minor resets to
**0** to mark the 10.x → 11.x major move.

## What was rebased, and onto what

Onto the **v11.1.0 tag**, not `upstream/main`, which was 38 commits past it. A released tag is a
tested point; a mid-development tip is not, and this uplift already carries enough new surface.
Those 38 commits are the next sync's problem, not this build's.

`pre-v16-upgrade` pins the last 10.6.x assembly (build 311) if a bisect is ever needed. All seven
branches rebased; five carried fork work, three hit conflicts.

## The conflicts, and how they were resolved

Two were mechanical — upstream and the fork adding at the same site:

- **`IntelligenceEngine`**: upstream rewrote the no-motion sleep branch for its HR-only Stage-0
  spine (#1801/#1806/#1813). Upstream's logic kept whole; the fork's `timedRead {}` instrumentation
  re-applied to its store read.
- **`BLEManager`**: upstream's link-epitaph frame tallies (#1809/#1820) and the fork's `BatteryDiag`
  per-channel wake counter now sit side by side. They answer different questions — "did anything
  arrive at all" vs "which channel is waking us, and how often" — so both belong.

The third was real, and worth stating plainly.

### Upstream built the same coach feature, with the opposite rule

Both had widened the LLM context with sleep detail the coach already held. The fork (#1817) emits
the stage breakdown **always**, with `—` on nights that recorded none. Upstream put it behind the
`includeDerivedTrends` toggle and **omits** absent fields, reasoning that `deep —` is one
substitution away from being read as zero deep sleep.

Both had tests; both could not hold. **The fork's rule was kept**, on the maintainer's call:

- A fixed schema is what stops the model inferring. A line whose columns appear and vanish between
  days invites "no deep field" to be read as zero — the same misreading upstream's rule guards
  against, arriving by the other door. `deep —` states the absence out loud.
- It is also the behaviour already on the phone. Reverting would have returned the default context
  to `rest 7.5h` — the exact silence #1817 was filed about.

Upstream's genuinely wide-only columns (wakes, SDNN, skin temperature) keep **its** omit-when-nil
rule: those are extra detail rather than part of a night's basic shape, so their absence carries no
meaning. Also kept from upstream: the static, engine-free `dayLine(_:wide:)` seam, and the bimodal
skin-temperature labelling (a strap deviation and an imported absolute °C share one column and must
be told apart, or every row of whichever kind lost the coin toss is misreported).

Upstream's narrow-line test was **inverted, not deleted** — the property it guards (no wide-only
leakage into the default context) still matters. Its wide-line test now also pins that stages are
not re-emitted in minutes beside the hours, which a naive merge did.

Android parity holds with no Kotlin change: `AiCoach.kt` already emits stages unconditionally in
hours with a `-` fallback.

## A pre-existing test bug, found on the way

`DailyTargetsTests.testSleepNeedComposesTheBodysDay` asserted 515 against a correct 520 — the
expectation omitted the debt term (a 20-minute deficit sits outside the 10-minute deadband, so a
quarter of it is asked back). The **code was right**; the test's arithmetic was short by one term.
It predates this uplift and was failing before it.

## What this build inherits from upstream

Notably: the HR-only sleep spine for straps that bank no motion (#1805/#1806/#1813), BLE link
epitaphs on disconnect (#1820), the strap-clock diagnostic that reads the answer instead of
asserting it (#1824), per-day phone-alarm wake times (#1859), a Health Connect permission split,
and the 11.0.0/11.1.0 release work itself.
