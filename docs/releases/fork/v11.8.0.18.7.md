# 11.8.0.18.7 (build 408)

The scrolling answer — found by the maintainer, not by this investigation — plus three LLM-summary
faults and the Integration file.

## The scroll lag was never a regression

Six theories died before the maintainer settled it by bisection on the device. The decisive
evidence, in the order it arrived:

1. **Build 17-2 (11.6.0, cut 09-14) lags identically.** That killed every theory that blamed work
   done on 09-19 — the per-tab summaries, the widget rebuild, the v11.8.0 uplift, and the
   coach-engine observation bug fixed in 18.4. There was no regression to find.
2. **Reduce Motion and Reduce Transparency changed nothing.** Not the OS chrome, not
   `staggeredAppear`.
3. **Removing exactly two cards fixed it**: Sleep's Night detail and Trends' Daily signals. And the
   whole page stayed slow with those cards moved to the very END of the scroll.

That last point is the diagnosis. A cost that follows a card regardless of its position is not
drawing — it is work paid per instance on every body evaluation.

Both cards are sparkline grids: Night detail draws **7** `StatTile` sparklines, Daily signals five
charts. `Sparkline` attached `.onContinuousHover`, `.contentShape(Rectangle())` and an
`.animation(_:value:)` to every instance, inside a `GeometryReader`.

Its own accessibility comment had said the affordance was pointer-only since it was written:

> The line is pointer-hover only (dead on touch)

So on an iPhone all of it was built and none of it could ever fire. The previous
`guard showsHover else { return }` gated the **callback**, which does not help — the cost is in
attaching the trackers, not in running them.

`showsHover` now defaults to whether a pointer can reach the view at all: iPad yes, iPhone no. The
modifiers are attached through one `@ViewBuilder` helper that keeps a single view type in both
branches, so this never changes view identity (the #519 lesson, in the gesture layer).

**Two earlier fixes stay.** 18.4's tab-root observation scoping and 18.6's `points` memoization were
both real costs and both correctly removed — they simply were not *this* cost. Shipping them was not
wrong; claiming they would fix the maintainer's symptom was.

### What the investigation got wrong, for the next time

Reading code found five plausible causes and zero real ones. The maintainer's
remove-one-card-at-a-time bisection found it in one pass. The fork's own instrumentation-first rule
exists for exactly this and was not applied to UI work:

> when a log can't attribute a cost, ship cheap measurement … never a speculative fix

Also worth recording: the Mac has only the **iOS 26.5 SDK** while the phone runs **iOS 27.0**. That
was a genuine finding and remains a real thing to fix, but it was not the cause — 17-2 and 18.6 lag
identically under the same SDK gap, and the sparkline fix is orthogonal to it.

## The summaries were inventing numbers

The Recap summary described **1.9 hours of rest, 75 bpm and 41 ms** for a day whose own card read
**7.9h, 64 bpm and 36 ms**.

Recap builds its facts from the `DayQualityScore` the card itself renders — the component evidence
strings, `"7.9h of 8.1h needed"`, are the literal text handed to the model. The numbers could not
have drifted. The model **fabricated** them outright, and nothing in the prompt forbade it.

All four prompts now carry an explicit verbatim-only rule (Today already had its own). A number that
is not in the facts must not appear, and a finding with no available figure is stated in words.

Separately, the sleep facts said only `THE NIGHT OF <key>`. A sleep row is keyed by the day the
session **ended**, so that key names the morning, not the evening — an invitation to narrate the
wrong calendar day. Now stated in full.

## Integration — the daily digest file

A new screen under Settings, beside Backup & Sync and deliberately not inside it.

| | Backup & Sync | Integration |
|---|---|---|
| Payload | whole database | a short digest |
| Name | dated `noop-backup-*.noopbak` | fixed, default `noop_to_muse.txt` |
| Lifecycle | accumulates, pruned by count | overwritten in place |
| Reader | a future NOOP | something that is not NOOP |

Configurable: destination folder (system picker, or NOOP's own Files-visible folder), filename,
the hour it generates, and whether to include the coach's written summaries. Plus **Generate now**
and **Preview without writing** — the preview builds the digest and shows it without touching the
folder, so the wearer can see exactly what would leave the device first.

**Contents:** today's partial state with all four target pairs and their derivations; last night's
full architecture (stages, efficiency, disturbances, respiration, SpO2, SDNN, skin temperature
labelled deviation-vs-absolute); yesterday's grade with every component's evidence; 14/30-day means;
the trailing grade run; and `derivedTrendsBlock` verbatim — training load, the sleep-debt ledger and
per-signal z-scores against the wearer's own baselines.

That last block is from Trends, included because every line of it is **daily** actionable ("acute
load is running above chronic", "2.3h short over 7 nights", "HRV z −1.4"). The 90-day slopes the
Trends charts draw are deliberately absent: nothing about a quarter-long trend changes what today
should look like.

Every absent value reads "not recorded" rather than vanishing — a reader diffing two days must be
able to tell a zero from a gap.

**Scope:** local export to user-owned storage. No server, account, network or third-party
destination, and nothing is read back — strictly narrower than the #1314 self-hosted push
`docs/SCOPE.md` already permits, which is a *network* export.

**The scheduled write passes `coach: nil`** on purpose. Holding an `AICoachEngine` on the tab shell
would subscribe it to all 32 of that object's `@Published` properties — the exact hazard 18.4
removed. The daily file carries the numbers; the coach paragraphs come from Generate now, on the
screen that already holds the engine.

## Also

- A **Regenerate** button on the Sleep, Recap and Trends summaries, matching Today's. Built as an
  overlay, because a `Button` nested inside another `Button`'s label is not independently tappable
  and would have toggled the section instead.
- **Ask the Coach is now scoped to its tab.** It seeds `pendingPrompt` with the summary being shown,
  so the chat opens as a follow-up to that reading instead of a cold start the wearer has to
  re-explain.
- `DayQualityComputer.previousDayKey`, with both day-key shifts now sharing one **UTC-pinned**
  helper. These keys are calendar labels, not instants; parsing them in the device's zone moves a
  day across a DST boundary.

## Verification

Both app targets compile. 2443 macOS tests, the only two failures being the pre-existing
`SkinTempAbsoluteDisplay` / `SleepCarriedStamp` pair already confirmed on a clean v11.8.0 worktree.

New tests: filename sanitising — which caught `"../../etc/passwd"` surviving as `-..-etc-passwd`,
harmless but ugly, so separators are now dropped rather than substituted — the cadence rule
including catch-up after a missed day, day-key inversion across month and leap boundaries,
not-recorded rendering, night-attribution labelling, efficiency normalising from both storage forms,
and the baseline block's three-day floor.
